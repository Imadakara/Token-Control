# Token Control — план развития до стратегии (ТЗ v0.02)

По ТЗ: `Personal Vault/Token Control Docs/ТЗ - MVP - Token Control v0.02.md`.
Предыдущий этап: [MVP - Plan.md](MVP%20-%20Plan.md) (фазы 0–5 выполнены),
описание имплементации — [MVP - Implementation.md](MVP%20-%20Implementation.md).

> **Суть витка:** вектор смещается от управления одним звездолётом к управлению
> флотилией. Новый жанр — пошаговая стратегия (референсы Homeworld, Warp To
> Sector One). ОВМ остаётся административно-вычислительным ресурсом в основе.
>
> **Внимание:** переход ломает модель данных (один корабль → таблица сущностей,
> общая очередь → приказы на сущность). Существующие миры **сбрасываются**;
> миграция данных игроков не делается (см. решение 9).

## Часть I. Принятые решения

### 1. `ships` → `entities`

Новая таблица; `ships` дропается в той же миграции:

```
entities (
  id uuid PK, player_id text FK → players.id,
  name text,                              -- «БОРТ-001», переименуемо игроком
  class_id text,                          -- ключ статичного каталога, не FK
  sector_id text, x, y double precision,
  docked_object_id uuid null,
  modules jsonb not null default '[]',    -- ModuleId[]
  hp int, hp_max int,
  priority smallint not null default 100, -- порядок раздачи ОВМ
  created_at timestamptz
)
```

- **`class_id` и `modules` — ключи статичного каталога** в
  `packages/shared/src/entities.ts`, а не таблицы БД. Классы и модули — это
  контент: типизированный, диффабельный, нужный и серверу (правила), и клиенту
  (лейблы). Таблица классов дала бы джойн на каждый чих и рассинхрон с TS-типами.
  Отдельная таблица `entity_modules` оправдана только когда появится установка и
  снятие модулей с инвентарём — это roadmap-фаза «производство» (ТЗ п. 81).
- **Стационарные объекты — тоже `entities`**, с `ENTITY_CLASSES[classId].mobile
  === false` (врата, будущие постройки). Именно это даёт требование ТЗ п. 2
  «список сущностей **и стационарных объектов** под управлением игрока» одним
  запросом к одной таблице.
- **`queues`**: PK → `(entity_id, slot)`; колонка `player_id` **остаётся**
  денормализованной с индексом — она нужна `lockPlayer` и свипу, иначе каждый тик
  свипа станет джойном. Слоты 1..`cfg.game.orderSlots` (дефолт 3).
- **`cargo`**: переезжает на сущность (`entity_id not null`, `player_id`
  сохраняется для дешёвых выборок). Вместимость берётся из
  `ENTITY_CLASSES[classId].cargoCapacity`, `cfg.game.cargoCapacity` становится
  дефолтом класса. Обоснование: ТЗ требует «добыча — если сущность в тех же
  координатах, что объект», то есть груз физически локализован; общий бездонный
  трюм игрока сломает производственные цепочки. Делаем сразу в фазе 6, иначе
  `executeAction` для `mine`/`pickup` придётся переписывать дважды.
- **`ships.docked_object_id`** → `entities.docked_object_id`; семантика та же, но
  стыковка становится приказом `interact`, а цель обязана иметь
  `props.dockable === true` (worldgen уже это ставит).
- **Совместимость:** `StateResponse.ship` сохраняется на фазы 6–7 как «первая
  сущность игрока по `created_at`», помеченная `@deprecated`. Это позволяет фазе 6
  быть чисто серверной и не ломать ни один существующий экран. Поле удаляется в
  фазе 8 вместе с `Queue.svelte`.

### 2. Один поток ОВМ на N очередей — строгий приоритет

**Правило.** Сущности игрока упорядочены по `(priority ASC, id ASC)`. ОВМ
вливается в голову очереди первой сущности; излишек завершённого приказа
каскадом уходит следующей сущности в том же порядке; остаток — в общий буфер с
капом. Приоритет переставляется игроком в дереве «Приказы» (`POST /fleet/priority`).

Почему приоритет, а не round-robin и не пропорция:

1. **Это строгое обобщение текущего движка.** При N=1 поведение бит-в-бит
   совпадает с сегодняшним `applyOvm` (`server/src/game/queue.ts:123`), и весь
   `server/test/queue.test.ts` (каскад, «НЕВЫПОЛНИМО», идемпотентность, кулдаун)
   продолжает проходить без правок.
2. **Сохраняется инвариант каскада излишка** — душа экономики ОВМ.
   Пропорциональное деление превращает излишек в N дробных остатков и порождает
   дрейф округления по `numeric(14,3)`.
3. **Честный статус-бар.** ТЗ п. 3 требует индивидуальный бар готовности при
   общем буфере. При приоритете одна сущность реально заполняется, остальные
   показывают `ОЖИДАНИЕ ПОТОКА` — это читаемо и правдиво. Round-robin даёт N вяло
   ползущих баров и ноль решений.
4. **Это и есть стратегия.** ОВМ — дефицитный административный ресурс;
   распределение внимания между кораблями и есть игровое решение.

**Реализация** (`server/src/game/queue.ts`):

- Тело текущего цикла `applyOvm` выносится в
  `pumpEntityQueue(ctx, entityId, rest): Promise<{ rest, executed, blockedByCooldown }>`.
- `applyOvm(ctx, ovm)` итерирует сущности по приоритету, прокидывая `rest`, и
  повторяет проход, пока хоть одна сущность выполнила приказ (завершение может
  разблокировать следующую).
- **Изменение поведения, требующее теста:** сущность, чья голова набрала
  стоимость, но стоит в кулдауне, больше не обрывает каскад (`break` на
  `queue.ts:155`), а **пропускается** — `rest` течёт дальше. Иначе один кулдаун
  морозит весь флот.
- **`lockPlayer` не меняется** и остаётся единственной точкой сериализации:
  `SELECT ovm_buffer FROM players FOR UPDATE`. Все сущности игрока под одним
  локом — нет порядка блокировок, нет дедлоков, нет гонок между очередями.
- `server/src/game/sweep.ts`: выборка меняется на джойн `queues × entities`,
  `selectDistinct(entities.playerId)`; транзакция на игрока остаётся как есть.
- Аварийный выход в конфиг: `game.ovmAllocation: 'priority' | 'split'`, дефолт
  `'priority'`; реализуем только `'priority'` — поле есть задел на калибровку без
  релиза (правится в `game_config`, hot-reload уже работает).

### 3. Модель приказов и вычисление доступности

`ActionType` → `OrderType` (`packages/shared/src/domain.ts`), с миграцией строк в
`queues` и `action_log`:

| было | стало | параметр |
|---|---|---|
| `jump_local` | `move` | `point` \| `object` |
| `dock` | `interact` | `object` (сервер сам решает стыковка/расстыковка) |
| `scan`, `analyze`, `mine`, `pickup`, `jump_hyper` | без изменений | как есть |
| — | `attack` | `object` |
| — | `special` | `{kind:'special', moduleId, ...}` |
| — | `upload_data` (ф. 10), `build_gate` (ф. 11) | `item` / `point` |

Переименовываем, а не сохраняем старые id: ТЗ переименовывает саму концепцию
(«очередь задач» → «приказы»), история журнала стоит дёшево, а `dock` как частный
случай `interact` иначе останется вечным исключением в валидаторе.

**Доступность считает сервер, отдельным эндпоинтом:**

```
GET /orders/available            → все сущности игрока
GET /orders/available?entityId=  → одна сущность
→ { entities: [{ entityId, orders: [{
      type, costOvm, available: boolean,
      reason: string | null,               // RU-строка, готовая к показу
      target: 'none'|'point'|'object'|'sector'|'item',
      candidates?: [{ objectId, label }]   // объекты в тех же координатах
  }] }] }
```

Почему эндпоинт, а не поле в `/state`: список — O(сущности × приказы × объекты
рядом), а `state_delta` пушится по WS на каждый тик начисления ОВМ
(`server/src/game/sweep.ts:42`). Раздувать самое горячее сообщение ради данных,
нужных только в момент «навёл + Enter», нельзя. Клиент кэширует ответ по
`entityId` и инвалидирует по `state_delta`.

Реализация — новый `server/src/game/orders.ts`, `listOrders(ctx, entity)`,
построенный **поверх существующего** `validateAction` (`server/src/game/actions.ts:65`)
с третьим режимом `'offer'` (≈ `activate`, но всегда возвращает
`{available, reason}` вместо броска). Это гарантирует, что UI никогда не
предложит приказ, который отвергнет `POST /orders/add`. Ключевой рефакторинг:
`getShip(ctx)` (`actions.ts:28`) исчезает, сущность передаётся явным аргументом в
`validateAction`/`executeAction`.

**Координаты.** ТЗ требует «те же координаты», текущий код — `isNear` с
`nearDistance = 10` (`actions.ts:39`). Вводим `sameCoords(entity, obj, cfg)` =
`hypot <= cfg.game.coordEpsilon`, дефолт `coordEpsilon = 10`. Точное равенство
float'ов не берём: `move` пишет точные координаты цели, но респавн и будущий
дрейф объектов это сломают.

### 4. Группы и групповые приказы

**Группа не хранится в БД — она вычисляется.**
`groupKey = ` `` `${sectorId}|${round(x/eps)}|${round(y/eps)}` `` отдаётся сервером
в составе `EntityState`.

Групповой приказ — веерная рассылка на этапе постановки:

```
POST /orders/add { entityIds: string[], order, params }
→ { results: [{ entityId, ok, reason? }], state }
```

Сервер валидирует каждую сущность независимо и ставит идентичный приказ в её
собственную очередь; невалидные пропускаются с причиной. Обоснование: движок
очередей остаётся строго по-сущностным, учёт ОВМ не усложняется, а расхождение
судеб (одну уничтожили, другая отстала) не портит общий объект-приказ. «Группа» в
Homeworld — это выделение в UI, а не доменная сущность. Групповое перемещение
работает само собой: `move` — телепорт, все прибывают одновременно.

### 5. База Знаний и Технологии — контент статикой, в БД только прогресс

- `packages/shared/src/knowledge.ts`: `KNOWLEDGE_ENTRIES: KnowledgeEntry[]`
  (`id, title, branch, body, tags[]`), `TECHS: Tech[]`
  (`id, title, branch, requires: TechId[], dataCost: { entryIds, ovm }, unlocks: Capability[]`).
- `Capability = {kind:'order', order} | {kind:'module', moduleId} | {kind:'class',
  classId} | {kind:'build', objectKind}` — единый плагин-пойнт, который читают
  `listOrders` и `validateAction`.
- Таблицы: `player_knowledge (player_id, entry_id, unlocked_at)` PK(player_id,
  entry_id); `player_tech (player_id, tech_id, researched_at)` PK(player_id, tech_id).

**«Загрузка данных в Базу Знаний» как игровое действие** (ТЗ п. 6) — приказ
`upload_data` с параметром `{kind:'item', itemType:'container:data-core'}`. Он
потребляет из трюма сущности контейнер с `contents: 'data-core'` — **worldgen уже
такие генерирует** (`server/src/game/worldgen.ts:97`); добавляется только
детерминированно выбираемый тем же `rng` `props.entryId`. Приказ стоит ОВМ и
разблокирует запись Базы Знаний.

Когда все `dataCost.entryIds` технологии открыты — она становится исследуемой:
`POST /tech/research { techId }` списывает `dataCost.ovm` из буфера мгновенно.
Это **не приказ**: исследование — действие интерфейса управления, а не флота.
Ноль новых типов объектов, максимум переиспользования существующей генерации.

### 6. Врата, Цепь Миров, один стартовый сектор

- **Личный домашний сектор.** `POST /auth/dev` больше не сажает всех в
  `world.startSector`: `homeSectorId = pickHomeSector(createRng(playerId + galaxySeed), world)`,
  пишется в новую колонку `players.home_sector_id`. Сетка галактики расширяется
  до 32×32 в `DEFAULT_WORLD`. Коллизии редки и безвредны — `objects` и так
  глобальны и разделяемы.
- **Соседство перестаёт быть правилом перемещения.** `sectorsAdjacent`
  (`worldgen.ts:46`) остаётся для тестов и генерации, но уходит из
  `validateAction('jump_hyper')` (`actions.ts:96`). Правило — граф Цепи Миров:
  новая глобальная таблица `sector_links (a_sector_id, b_sector_id, created_at)`,
  PK по упорядоченной паре, неориентированная (ТЗ: «двустороннее перемещение»).
- **`jump_hyper` доступен, если:** (а) исследована технология `nav.hyperjump`,
  (б) в исходном секторе есть сущность класса `gate`, (в) `sector_links`
  содержит ребро source–destination. Иначе — `НЕТ СВЯЗИ В ЦЕПИ МИРОВ`.
- **Врата — сущность** `classId: 'gate'`, `mobile: false`, создаётся приказом
  `build_gate` (цель — точка в домашнем секторе), `actionCosts.build_gate = 250 000`.
  Стоимость **намеренно выше** `ovmBufferCap = 100 000`: врата физически
  невозможно купить из буфера, их можно только накопить в счётчике самого
  приказа — ровно то «большое число сконвертированной работы ИИ-агента», которого
  требует ТЗ п. 4. Движок это уже умеет, менять ничего не надо.
- По завершении `build_gate` сервер вставляет ребро в `sector_links`, соединяя
  домашний сектор со случайным сектором, у которого уже есть врата (или с
  сектором-хабом, если игрок первый) — автоподключение к Цепи по ТЗ.
- **Точка монетизации:** `POST /chain/connect { keyId }` потребляет строку
  `chain_keys (id, player_id, target_sector_id null, source, consumed_at)` и
  создаёт ребро в конкретный мир. Ключи выдаёт `routes/debug.ts` (уже защищён
  `pid === 'dev:DEBUG'`). Платёж — Steam Inventory/DLC — уезжает в фазу 99.
  Разрабатываем **механику**, а не биллинг.

### 7. Локальный ассистент — ничего не встраиваем в сборку

Клиент ходит в OpenAI-совместимый `/v1/chat/completions` по настраиваемому base
URL, дефолт `http://127.0.0.1:11434/v1` (Ollama), модель `qwen2.5:3b-instruct`.

Живёт в веб-части клиента (`client/src/lib/assistant.ts`), транспорт — через
Tauri-плагин HTTP (обход CORS). **Не в Rust:** коннектор — критичный по
надёжности демон, нечего мешать к нему чат. **Не на сервере:** модель крутится на
машине игрока, а сервер обязан оставаться дешёвым и мультиарендным.

Авторитетность делится пополам:

```
POST /assistant/prepare { question }
→ { contextEntries: KnowledgeEntry[], systemPrompt, allowedTools }
```

Сервер списывает `cfg.game.assistantCostOvm` из буфера **до** выдачи контекста и
возвращает только те записи Базы Знаний, которые игрок реально открыл (ТЗ п. 7:
«в рамках известной ему информации»). Ответ модели сервер не видит и не доверяет
ему.

Команды: модель возвращает JSON-tool-call из фиксированной крошечной схемы
(`{tool:'order.add', entityId, order, params}`, `{tool:'ui.screen', screen}`),
клиент валидирует его тем же zod-типом из `shared` и дёргает обычный REST.
Ассистент физически не может сделать того, чего не может игрок.

**Опциональность по построению:** если base URL недоступен — экран «Ассистент»
показывает `ЛОКАЛЬНАЯ МОДЕЛЬ НЕ ОБНАРУЖЕНА` и подсказку по установке, остальные
экраны не затронуты. Ноль зависимостей сборки, ноль гигабайтов в инсталляторе,
ноль лицензионных вопросов.

### 8. Клиент: снятие тройного хардкода и фикс клавиатуры

- **Единый реестр экранов** `client/src/lib/screens.ts`:
  `SCREENS: { id, key, label, component }[]`, тип `Screen` выводится из него.
  `App.svelte` рендерит компонент из реестра вместо цепочки `{#if}`
  (`App.svelte:79-85`), а `MENU` (`App.svelte:16-24`) становится этим же массивом.
  Одна правка вместо трёх.
- **Фикс бага с цифрами и текстовым вводом.** Сейчас обработчик `App.svelte:42`
  зарегистрирован раньше экранных, поэтому `stopPropagation` в экранах его не
  останавливает — ввод цифры в чат ассистента переключит экран. Вводим в
  `game.svelte.ts` два флага: `inputFocused` (по focus/blur любого
  `input`/`textarea`) и `modalDepth` (счётчик открытых оверлеев); `onKey` в
  `App.svelte` выходит первой же строкой, если любой взведён. **Это обязано
  приземлиться в фазе 7, до появления чата.**
- **Общие компоненты** в `client/src/lib/terminal/`: `Overlay.svelte` (бокс
  `.panel.overlay` + Esc + авторегистрация в `modalDepth`), `Confirm.svelte`,
  `ListPicker.svelte` (курсор, ↑↓, Enter, строка фильтра), `Tree.svelte`
  (сворачиваемые узлы с плоской клавиатурной навигацией). Эталон для извлечения —
  `Queue.svelte:128-156` и слоёная обработка клавиш `Queue.svelte:66-93`. `Tree`
  переиспользуется и в «Приказах», и в «Базе Знаний».
- Меню: экранов станет 11 — цифры `1..9` + `0`, плюс циклический `Tab`/`Shift+Tab`.

### 9. Стратегия миграции: вайп мира, но не разрушительной миграцией

- Миграции остаются **аддитивными и forward-only** (их применяет
  `server/src/db/migrate.ts` на старте): `0003` создаёт `entities`, бэкфиллит из
  `ships`, дропает `ships`. Тесты и живой dev-игрок продолжают работать.
- Новый `server/scripts/wipe.ts` делает `TRUNCATE` игрового мира, **не трогая
  `credit_ledger`** — иначе сломается монотонность `packetSeq` в rusqlite
  коннектора и дедупликация начислений (риск №3 в MVP-плане).

Обоснование: проект дорелизный, живой игрок один, а меняется всё сразу —
домашние сектора, правила прыжка, привязка трюма, id приказов. Аккуратные
data-миграции стоят дней, вайп — одной команды. Единственная ценность,
`players.ovm_buffer`, восстанавливается коннектором за сессию.

## Часть II. Фазы

Порядок выбран так, чтобы играбельность не пропадала: 6 — сервер под старым UI,
7 — UI-каркас, 8 — новый основной цикл, дальше содержательные надстройки.

### Фаза 6 — Сервер: флот и по-сущностные очереди (4–5 дней) — ✅ выполнена

**Цель:** движок работает на N сущностей, клиент об этом ещё не знает.

- **shared**: новый `entities.ts` (`ENTITY_CLASSES`, `MODULES`, `EntityClassId`,

> целиком всем игрокам: топология Цепи — это не секретное содержимое сектора
> (которое по-прежнему скрыто скан/анализом), а координатная карта маршрутов,
> как и сами ID секторов.
>
> Найдено и исправлено при разработке (до прогона тестов): тестовый сценарий
> для `/debug/chain-key` изначально был написан наоборот — ожидал, что

> сам тест, а не код, плюс добавлен прямой DB-сид ключей (`grantKey`) для

>
> Тесты — новый `chain.test.ts` (7 тестов: гейт без техи/без врат на

## Часть III. Недоспецифицированное в ТЗ и минимальные развязки

1. **Боёвка** (ТЗ п. 3.2, ToDo). Детерминированный одиночный размен без
   NPC-ответа и таймеров: `attack` требует модуль с `damage`, совпадение
   координат и `props.attackable` у цели; исполнение вычитает суммарный урон
   модулей из `props.hp`, на нуле объект уничтожается и роняет контейнер
   (переиспользует `pickup`). У сущностей `hp`/`hp_max` заводятся сразу, но PvP и
   ответный огонь явно отложены. Это разблокирует список приказов, не проектируя
   боевую систему.
2. **Что открывают технологии** (ТЗ п. 6, ToDo). 3 ветки, 6 технологий, каждая —
   одна строка каталога:
   - **Навигация**: `nav.survey` (сниженная стоимость `scan`) → `nav.hyperjump`
     (открывает `build_gate` и `jump_hyper`);
   - **Промышленность**: `ind.mining` (модуль `mining_laser`) → `ind.refinery`
     (`special: refine`);
   - **Оборона**: `def.weapons` (модуль `railgun` + приказ `attack`).
3. **Монетизация** (ТЗ п. 4). Механика (`chain_keys` + `POST /chain/connect`) —
   фаза 11, ключи выдаёт debug-роут; витрина Steam — фаза 99. Разработка не
   блокируется отсутствием биллинга.
4. **«Статус» сущности** (ТЗ п. 2 требует параметр, не определяя его).
   Вычисляемый enum: `ПРОСТОЙ | ВЫПОЛНЯЕТ: <приказ> | ОЖИДАНИЕ ПОТОКА |
   ПРИСТЫКОВАН | ПОВРЕЖДЁН`.
5. **«Название» сущности.** Автогенерация `<КЛАСС>-<NNN>` при создании +
   `POST /fleet/rename`. Дёшево и повышает привязанность игрока к флоту.
6. **Число слотов приказов на сущность.** ТЗ не называет — берём
   `cfg.game.orderSlots = 3`, как сейчас, с возможностью расширения технологией
   без релиза.
