## Часть I. MVP (фазы 1–5, ТЗ v0.01)

## Общая картина

```
┌────────────────────── клиент (Tauri) ──────────────────────┐
│  веб-UI (Svelte 5)          Rust-коннектор                 │
│  7 экранов терминала        ~/.claude/projects/**/*.jsonl  │
│  очередь, карты, трюм       парсинг → дедуп → ОВМ → outbox │
│        │  HTTP/WS                 │ HTTP (только числа)    │
└────────┼──────────────────────────┼────────────────────────┘
         ▼                          ▼
┌──────────────────── сервер (Node/Fastify) ─────────────────┐
│  авторитетная симуляция: очередь, действия, мир, лимиты    │
│  PostgreSQL (Drizzle): 11 таблиц, весь прогресс в БД       │
└────────────────────────────────────────────────────────────┘
```

Принципы, выдержанные во всех фазах:

- **Сервер — единственный источник истины** (ТЗ п. 3.2). Клиент не меняет
  игровое состояние сам; любые мутации — HTTP-команды, применяемые сервером
  в транзакциях PostgreSQL. На сервере нет in-memory игрового состояния —
  рестарт «бесплатен».
- **Всё калибруемое — в БД** (ТЗ п. 12.2): стоимости, формула, лимиты,
  параметры генерации лежат в таблице `game_config` и перечитываются без
  рестарта (см. Фазу 5).
- **Приватность** (ТЗ п. 10): коннектор десериализует только числовые поля и
  идентификаторы; на сервер уходят только числа.

## Фаза 1 — сервер: БД, генерация мира, state API

### Схема БД — `server/src/db/schema.ts`

| Таблица | Назначение | Ключевые детали |
|---|---|---|
| `players` | игроки | `id` = `dev:<имя>` (позже `steam:<id>`); `steam_id` unique nullable — колонка готова к Фазе 6; `ovm_buffer numeric(14,3)` — системный буфер ОВМ (ТЗ п. 5) |
| `ships` | корабли | PK = `player_id` (1 корабль на игрока в MVP); `sector_id`, `x`, `y`, `docked_object_id` |
| `queues` | очередь задач | PK (`player_id`,`slot`), slot 1–3; `cost_ovm`, `progress_ovm` numeric, `status` waiting/active; `activated_at` — момент активации для кулдауна исполнения |
| `sectors` | созданные сектора | `id` = `"gx:gy"`; строка появляется при первом визите (ленивая генерация) |
| `objects` | объекты секторов | `type` station/asteroid/container/phenomenon; `props jsonb` (скрытые свойства); `resource_amount`/`max_resource`/`respawn_at` для регенерации |
| `known_objects` | что открыто игроку | PK (`player_id`,`object_id`); `level` = scanned \| analyzed (ТЗ: скан даёт позиции, анализ — свойства) |
| `visited_sectors` | посещённые сектора | для карты галактики (ТЗ п. 4.2.3) |
| `cargo` | трюм | `kind` resource/object, `item_type`, `qty`, `props` |
| `action_log` | журнал | `action`, `result` (строка терминала), `details jsonb` |
| `credit_ledger` | входящие пакеты ОВМ | **UNIQUE(`player_id`,`packet_seq`)** — фундамент идемпотентности; хранит и `ovm_submitted`, и `ovm_accepted` + токены по типам — данные для калибровки N (ТЗ п. 13.1) копятся с первого дня |
| `game_config` | серверный конфиг | key/value jsonb: ключи `game` и `world` |

Миграции генерируются `drizzle-kit generate` (SQL в `src/db/migrations/`) и
применяются при старте сервера и в тестах (`db/migrate.ts`). Существующие
миграции: `0000_init`; `0001_packet_seq_bigint` (packet_seq расширен до
bigint); `0002_queue_activated_at` (+ ручной бэкфилл `now()` для уже активных
задач — свип не должен их потерять).

### Детерминированная генерация мира — `game/rng.ts`, `game/worldgen.ts`, `game/world.ts`

- PRNG: строковый сид → `xmur3`-хэш → `mulberry32`. Сид сектора =
  `"<galaxySeed>/<sectorId>"`, поэтому один и тот же мир воспроизводим на любом
  окружении (проверяется тестом).
- Галактика — сетка `galaxyWidth × galaxyHeight` (10×10), сектора адресуются
  `"gx:gy"`; соседство — манхэттенское расстояние 1 (для гиперпрыжка, ТЗ п. 6.3).
- Содержимое сектора (ТЗ п. 8): станция ≤ 1 (60 %), 3–8 астероидов (руда
  ferrum/silicium/iridium, запас 5–20), 0–3 контейнера, 0–2 феномена; координаты
  в диапазоне ±1000.
- **Ленивая генерация**: `ensureSectorGenerated` создаёт сектор и объекты при
  первом обращении. Гонка двух одновременных запросов снята `INSERT … ON
  CONFLICT DO NOTHING` c `RETURNING`: объекты вставляет только та транзакция,
  которая реально создала строку сектора.

### Авторизация (dev-заглушка) — `routes/auth.ts`

`POST /auth/dev {playerId}` (валидация `[\w-]{1,64}`) → при первом входе
создаёт игрока и корабль в стартовом секторе `5:5` (позиция 0:0), генерирует
сектор, помечает посещённым; возвращает JWT (`@fastify/jwt`, payload `{pid}`).
Все остальные маршруты защищены `app.authenticate` (Bearer). Steam auth ticket
(ТЗ п. 3.1) подключится в Фазе 6 тем же сессионным слоем.

### API снапшотов

- `GET /state` → `StateResponse`: корабль, очередь, буфер ОВМ, трюм, вместимость.
  Сборка вынесена в `game/state.ts::buildState` — переиспользуется маршрутами
  очереди, начислений и WS-пушем.
- `GET /map/sector` → только объекты, открытые игроку сканированием; `props` и
  `resource_amount` отдаются **только** при `level = analyzed` (ТЗ п. 6.5).
- `GET /map/galaxy` → размеры сетки, текущий сектор, посещённые сектора.
- `GET /config` → игровой конфиг (стоимости, формула, лимиты) — публичный,
  его же читает коннектор.

### Конфиг — `game/config.ts`

`loadServerConfig` читает ключи `game` и `world` из `game_config`; отсутствующие
засеваются дефолтами из `@tokencontrol/shared` (`DEFAULT_GAME_CONFIG`) и
`worldgen.ts` (`DEFAULT_WORLD`). Слияние мягкое (`{...defaults, ...stored}`) —
новые поля конфига не ломают старые записи БД.

Дефолты MVP: стоимости 10/100/250/1000 (ТЗ п. 6); формула kCacheW=1,
kCacheR=0.1, N=1000 (ТЗ п. 7.3); кап буфера 100 000 (ТЗ п. 5); лимиты
500/мин, 10 000/час, 100 000/сутки (ТЗ п. 9); трюм 100; радиус «возле» 10;
кулдаун исполнения задачи 3 с (`taskCooldownSec`).

## Фаза 2 — движок очереди, 7 действий, начисления

### Модель очереди — `game/queue.ts`

Инварианты (ТЗ п. 5):

1. Максимум 3 задачи, слоты компактны (1..n без дыр); по мере выполнения
   задачи сдвигаются вверх (2→1, 3→2).
2. Слот 1 — единственный активный; ОВМ вливаются только в него.
3. `promoteQueue` — уплотняет слоты и активирует голову с валидацией (ставя
   `activated_at`); если условие не выполняется — «НЕВЫПОЛНИМО» + журнал,
   задача удаляется, цикл повторяется для следующей.
4. `applyOvm(ovm)` — каскад начисления. Перед КАЖДОЙ тратой голова
   перевалидируется: невыполнимая задача пропускается, а её накопленный
   прогресс **возвращается в каскад** — ОВМ на невыполнимое не расходуются
   (сгорание прогресса осталось только при ручном удалении). Голова, набравшая
   стоимость, исполняется не раньше кулдауна (`taskCooldownSec`, 3 с) после
   активации — довершает её серверный свип (`game/sweep.ts`, тик 1 с),
   который также пушит событие завершения и состояние в WS. Излишек переходит
   в следующую задачу; при пустой очереди — в буфер с капом (переполнение
   игнорируется).
5. Постановка (`addTask`): при непустом буфере ОВМ из него сразу «вливаются» в
   счётчик новой задачи (prefill = min(буфер, стоимость)); полностью закрытая
   буфером задача всё равно ждёт кулдаун — мгновенного исполнения нет, клиент
   анимирует заполнение бара по `activatedAt`.
6. Удаление: прогресс сгорает (подтверждение — на клиенте), запись в журнал.
7. Перестановка: только слоты 2↔3, через временный слот 99 (PK-констрейнт).

События завершения/пропуска (`QueueEvent`) накапливаются в `ActionCtx.events`
внутри транзакции и после коммита пушатся в WS как `journal` — клиент пишет в
строку терминала «ЗАДАЧА ВЫПОЛНЕНА: …» и обновляет журнал.

Все операции выполняются внутри `db.transaction` с блокировкой строки игрока
(`SELECT … FOR UPDATE` в `lockPlayer`) — конкурирующие начисления и команды
игрока сериализуются на уровне БД.

### Действия — `game/actions.ts`

Ключевое проектное решение — **два режима валидации**:

- `enqueue` (постановка): только статические условия — цель существует,
  параметры корректны, сектор в пределах галактики. Позиционные условия
  («корабль возле») НЕ проверяются — иначе была бы невозможна осмысленная
  очередь «прыжок к астероиду → анализ → добыча»: условие анализа выполнит сам
  прыжок.
- `activate` (активация головы и повторно перед исполнением): полная проверка.
  Провал → «НЕВЫПОЛНИМО» + пропуск (ровно семантика ТЗ п. 5: «условие перестало
  выполняться к моменту, когда задача стала активной»).

| Действие | Условие (activate) | Параметр | Результат | Стоимость |
|---|---|---|---|---|
| scan | всегда | — | все объекты сектора → `known_objects(scanned)`; сектор догенерируется при необходимости | 10 |
| jump_local | цель в текущем секторе (для объекта) | точка или объект | корабль в точке/у объекта; автоотстыковка | 100 |
| jump_hyper | сектор соседний (манхэттен=1) | сектор | перенос в (0,0) целевого сектора; генерация + пометка «посещён»; автоотстыковка | 1000 |
| dock | станция в радиусе `nearDistance` | — | `docked_object_id` = станция | 10 |
| analyze | возле объекта | объект | `known_objects` → analyzed (upsert): открываются `props` и запасы | 100 |
| mine | возле объекта, запас > 0, трюм не полон | объект | −1 запас (при 0 ставится `respawn_at`); +1 ресурс в трюм (upsert строки) | 100 |
| pickup | возле контейнера, трюм не полон | объект | объект → трюм (kind=object); удаляются `known_objects`-ссылки всех игроков, затем объект | 10 |

Расстыковка — мгновенная и бесплатная (ТЗ п. 6.4): отдельный
`POST /ship/undock` вне очереди.

«Возле» = евклидово расстояние ≤ `nearDistance` (конфиг, 10). Прыжок к объекту
ставит корабль ровно в его координаты, так что условие гарантированно
выполняется.

### Начисления — `game/credits.ts`

`POST /credits/submit {packetSeq, ovm, tokens, intervalStart, intervalEnd}` —
одна транзакция:

1. `lockPlayer` (FOR UPDATE) — сериализация с командами игрока.
2. Проверка повтора: если `(player_id, packet_seq)` уже в `credit_ledger` —
   вернуть прежний `{accepted, clipped}` и **ничего не начислять**. Повтор
   пакета после обрыва сети/рестарта безопасен (ТЗ п. 11: идемпотентность).
3. Анти-абуз (ТЗ п. 9): по леджеру считается сумма `ovm_accepted` в окнах
   1 мин / 1 час / 24 ч; `accepted = min(submitted, остаток самого узкого
   окна)`. Излишек **мягко урезается** (`clipped`), не реджектится и не банит.
4. Запись в леджер (submitted и accepted раздельно — материал для калибровки).
5. `applyOvm(accepted)` — каскад в очередь/буфер.

После транзакции маршрут пушит свежий `StateResponse` в WS игрока.

### Регенерация ресурсов — `game/regen.ts`

`setInterval` 60 с: `UPDATE objects SET resource_amount = max_resource,
respawn_at = NULL WHERE respawn_at <= now()`. Время восстановления —
`world.respawnMinutes` (30) — выставляется при исчерпании в `mine`.

### WebSocket — `ws.ts`, `app.ts`

`GET /ws?token=<jwt>` (браузерный WebSocket не умеет заголовки — токен в
query). Реестр `WsRegistry`: множество сокетов на игрока, `push(pid, msg)` и
`broadcast(msg)`. Сообщения (типы в shared): `state_delta` (после каждой
мутации), `config_changed` (Фаза 5). Латентность 1–5 с по ТЗ п. 11 позволила
обойтись без дифф-протокола — шлётся полный снапшот.

### Инструменты и тесты

- `scripts/feed.ts` — «фейковый коннектор»: авторизуется, шлёт синтетические
  пакеты (packetSeq = Date.now()); использовался до Фазы 4 и остаётся удобным
  для отладки баланса.
- Тесты (`server/test/*.test.ts`, vitest, 20 шт.): детерминизм и границы
  worldgen; auth/state/maps/config; и сценарии движка — полный цикл
  скан→прыжок→анализ→добыча, мгновенное исполнение из буфера, «НЕВЫПОЛНИМО»
  после ухода от цели, сгорание прогресса при удалении, перестановка 2↔3,
  идемпотентность повторного пакета, урезание по минутному лимиту, кап буфера
  100 000, гиперпрыжок только в соседний сектор. Тестовая БД пересоздаётся на
  файл (`DROP/CREATE DATABASE tokencontrol_test`), поэтому файлы выполняются
  последовательно (`vitest.config.ts: fileParallelism false`). HTTP — через
  `app.inject` без сокетов.

## Фаза 3 — терминальный UI (Svelte 5)

### Архитектура клиента

- `lib/api.ts` — типизированный клиент поверх `fetch` (типы из
  `@tokencontrol/shared`), JWT в localStorage; `connectWs` с экспоненциальным
  реконнектом (1→15 с).
- `lib/game.svelte.ts` — единый стор на рунах Svelte 5 (`$state` в полях
  класса): состояние игры, конфиг, карты, журнал, экран, режим выбора цели,
  строка сообщений. Обновление: WS `state_delta` + поллинг 5 с (+ тихое
  обновление карт после каждого снапшота). `ratePerMin` — клиентская оценка
  входящего потока по дельте (буфер + прогрессы задач) во времени.
- Постановка действия (`chooseAction`): scan/dock уходят сразу; действия с
  параметром включают **pick-режим** (`game.pick = {action, target}`) и
  переключают на соответствующую карту; Enter на карте собирает `ActionParams`
  и вызывает `queue/add`; Esc — отмена (глобально в `App.svelte`).

### Экраны (ТЗ п. 4.2) — `src/screens/`

Строка сообщений терминала: завершения задач приходят WS-пушем `journal` —
«ЗАДАЧА ВЫПОЛНЕНА: …» / «НЕВЫПОЛНИМО: …». Индикатор потока в шапке затухает до
нуля после 60 с без притока (сессия агента завершилась) — иначе последнее
значение «зависало» навсегда.

### Оболочка — `App.svelte`

Шапка-телеметрия (ТЗ п. 4.3): индикатор связи, входящий поток ОВМ/мин,
прогресс-бар активного слота (или «очередь пуста → буфер»). Меню экранов
цифрами 1–7 и мышью; строка сообщений терминала внизу (`game.say`). Вся
клавиатура — `svelte:window onkeydown` с проверкой активного экрана;
`lib/terminal/keys.ts` нормализует легаси-имена клавиш (`Down`→`ArrowDown`).

### Стилистика (ТЗ п. 4.1)

Моноширинный шрифт, палитра из двух акцентов (зелёный фосфор + янтарь) в
CSS-переменных (`app.css`), псевдографика в `<pre>`. CRT — один статичный
CSS-слой (`Crt.svelte`: сканлайны repeating-gradient + виньетка), отключаемый,
без анимаций и canvas — нулевая фоновая нагрузка.

### Верификация

Полный ручной цикл пройден в браузере через реальный сервер: вход → скан
(мгновенно из буфера) → прыжок к астероиду → очередь «анализ + добыча» →
подача ОВМ → FERRUM×1 в трюме, журнал и статус корректны; WS-пуш обновляет
экран без перезагрузки.

## Фаза 4 — коннектор Claude Code (Rust, в Tauri)

### Поток данных

```
~/.claude/projects/**/*.jsonl
  → рескан каждые 5 с (walkdir; размер файла > сохранённого офсета?)
  → parser: дочитать с офсета ТОЛЬКО полные строки; type=="assistant" && usage
  → store (SQLite, одна транзакция на цикл):
      INSERT OR IGNORE в seen (дедуп) → только новые записи суммируются
      офсеты файлов обновляются
      T = in + out + kW·cache_w + kR·cache_r;  ОВМ = T/N + остаток
      пакет → outbox (packetSeq = AUTOINCREMENT)
  → submit: НЕМЕДЛЕННО при свежих токенах, иначе ретраи outbox каждые 15 с;
      пакет удаляется из outbox ТОЛЬКО после ack сервера
```

Статус агента: «работает» = хоть один файл логов **вырос** за последние
120 с (`ACTIVITY_WINDOW`), в статус входит `lastActivitySecs`. Наличие файлов
активностью не считается — раньше это давало вечное «ОБНАРУЖЕН» при
выключенном Claude Code.

### Модули — `client/src-tauri/src/connector/`

**`parser.rs`.** Целевая структура десериализации содержит только: `type`,
`uuid`, `requestId`, `message.model`, `message.usage.{input_tokens,
output_tokens, cache_creation_input_tokens, cache_read_input_tokens}` — текст
сообщений в типы не попадает (ТЗ п. 10). Не-assistant записи, записи без
usage и невалидный JSON молча пропускаются (в реальных файлах встречаются
посторонние форматы — проверено на живых логах). `read_from_offset`:
- офсет продвигается только за строки, завершённые `\n` — недописанная
  последняя строка дочитается в следующем цикле (ТЗ п. 7.2);
- `offset > len(file)` (усечение/ротация) → чтение с нуля.

**`store.rs`** — SQLite (rusqlite, WAL):
- `file_offsets(path, offset)`;
- `seen(id)` — **глобальный** дедуп-индекс: ключ `requestId` (иначе `uuid`);
  resume/fork сессий, дублирующие записи в новых файлах, не задваивают
  начисление (ТЗ п. 7.2);
- `outbox(seq AUTOINCREMENT, ovm, токены, интервал)` — оффлайн-буфер (ТЗ
  п. 3.2): пакеты переживают отсутствие сети и рестарты, удаляются по ack;
- `meta`: `remainder` (дробный остаток ОВМ сверх точности 0.001 — точность
  пакета согласована с `numeric(14,3)` сервера), `baseline_done`.
- `commit_scan` — атомарно: дедуп + офсеты + конвертация + пакет. Крах между
  циклами не приводит ни к потере, ни к задвоению.

**Baseline.** При первом запуске вся существующая история индексируется с
`credit=false`: id попадают в `seen`, офсеты — на EOF, **ничего не
начисляется**. Засчитываются только токены, потраченные после установки.

**`submit.rs`** — блокирующий reqwest: `GET /config` (коэффициенты формулы —
серверная калибровка без обновления клиента, ТЗ п. 7.3; перечитываются раз в
цикл отправки) и `POST /credits/submit` (Bearer). Ошибка сети/сервера просто
оставляет пакеты в outbox до следующей попытки.

**`mod.rs`** — цикл в отдельном std-потоке; статус (`ConnectorStatus`:
активность агента + давность, файлов, записей засчитано, outbox, последний
пакет, ошибка) отправляется в канал после каждого шага. Решение
«рескан-таймер вместо FS-watcher»: на Windows notify-события ненадёжны, а
рескан по размеру файлов раз в 5 с прост и является источником истины;
свежие токены отправляются немедленно, так что задержка «работа агента →
ОВМ в игре» — единицы секунд.

### Интеграция с приложением

- `lib.rs`: Tauri-команды `connector_start(serverUrl, token)` /
  `connector_stop`; поток статусов ретранслируется в веб-UI событием
  `connector-status`. SQLite живёт в `app_data_dir()/connector.sqlite`.
- `lib/connector.svelte.ts` (веб): детект Tauri по `__TAURI_INTERNALS__`,
  динамический импорт `@tauri-apps/api`; `game.start()` после логина передаёт
  токен коннектору. В браузерной сборке — честный фолбэк «недоступен».
- `bin/connector_cli.rs` — тот же цикл без окна (для отладки):
  `cargo run --bin connector_cli -- <player> [server] [projectsDir]`.

### Верификация

- 9 cargo-тестов: парсинг usage, пропуск чужих записей, fallback uuid,
  недописанная строка (офсет не двигается, дочитывание корректно), усечение
  файла, глобальный дедуп, перенос остатка (0.5 + 0.501 → 1.001), baseline без
  начисления, ack.
- Живой E2E: коннектор на реальных логах (32 файла) прошёл baseline, засчитал
  свежие записи текущей Claude Code-сессии; в леджере пакеты с
  cache_read ≈ 310–390 тыс. токенов → ~32–41 ОВМ (формула сходится).
- Рестарт-тест: kill процесса → повторный запуск → начислено только новое
  (буфер 162.3 → 261.1, без перезачисления истории).
- В десктоп-окне: игрок вошёл, коннектор стартовал автоматически, буфер
  40.1 → 121.9 ОВМ за ~90 с реальной работы агента.

## Фаза 5 — надёжность и полировка

### Переживание рестартов (ТЗ п. 11)

Было заложено архитектурно и проверено: сервер — весь прогресс в PostgreSQL,
мутации транзакционны, in-memory состояния нет; клиент — офсеты/дедуп/outbox
коннектора в SQLite, токен сессии в localStorage; идемпотентность
`credits.submit` покрывает повтор неподтверждённых пакетов после обрыва.

### Трей и «тихий» режим (ТЗ п. 11) — `lib.rs`

- Tauri-фича `tray-icon`: иконка в трее с меню «Показать терминал» / «Выход».
- Закрытие окна перехватывается (`CloseRequested` → `hide()` +
  `prevent_close()`) — терминал сворачивается в трей, Rust-коннектор
  продолжает считать ОВМ.
- Веб-часть при скрытом окне (`visibilitychange`) останавливает поллинг
  сервера; CRT статичен → потребление в покое ~нулевое. При показе окна —
  немедленный refresh.

### Локализация EN+RU (ТЗ п. 11) — `lib/i18n.svelte.ts`

Русские строки интерфейса служат ключами словаря (`t('ОЧЕРЕДЬ')` → `QUEUE`):
компоненты остаются читаемыми, EN-словарь — один файл (~100 записей).
Переключение — Настройки [E], выбор в localStorage, применяется реактивно
(руна в классе i18n). Серверные строки журнала в MVP остаются RU (контент, не
хром интерфейса) — вынос в клиентскую локализацию отмечен как будущая работа.

### Hot-reload конфига (ТЗ п. 12.2) — `server/src/index.ts`

Раз в 60 с сервер перечитывает `game_config`; при изменении — `Object.assign`
в решённый конфиг (все маршруты видят новые значения) и WS-broadcast
`config_changed` всем подключённым клиентам (UI обновляет стоимости в меню
действий без перезагрузки). Правка баланса = `UPDATE game_config …` в БД.

### Запуск одной командой

- `npm run desktop` (корень) → `tauri dev` в client → `beforeDevCommand` =
  `scripts/dev-stack.mjs`: проверяет порты и действует по ситуации —
  наш vite уже на 5173 → переиспользует работающий стек (только окно);
  работает только игровой сервер (8787) → доподнимает один vite;
  порт занят посторонним → понятная ошибка вместо стектрейса vite;
  всё свободно → полный стек: `predev` поднимает PostgreSQL
  (`docker compose up -d db`), затем сервер (:8787) + vite (:5173) → окно.
- `default-run = "app"` в Cargo.toml (в пакете два бинаря — окно и CLI).
- Сервер читает порт из `GAME_SERVER_PORT`, а не `PORT` — переменную `PORT`
  подставляют превью-раннеры и она ломала выбор порта.

## Отступления от буквы ТЗ и осознанные упрощения

| Решение | Мотив |
|---|---|
| Валидация на постановке — только статическая | Иначе невозможна очередь «прыжок → действие у цели»; полная проверка перенесена на активацию, что соответствует духу ТЗ п. 5 |
| Рескан-таймер вместо FS-watcher | Надёжнее на Windows; латентность ≤10 с не важна при батчах 30–60 с. Watcher — возможная оптимизация позже |
| Стоимость jump_local не масштабируется от дистанции | ТЗ допускает («допустимо масштабирование») — отложено до калибровки |
| `visited_sectors` — отдельная таблица | В ТЗ не перечислена, но нужна карте галактики (посещённые сектора — пер-игрок) |
| WS шлёт полный снапшот, не диффы | Допустимая задержка 1–5 с (ТЗ п. 11) делает диффы преждевременной оптимизацией |
| Поток ОВМ/мин в шапке — клиентская оценка | Сервер не считает rate; оценка по дельте (буфер+прогресс) достаточна для индикации |
| Буфер «вливается» в задачу только при постановке | Ровно по ТЗ п. 5; промежуточных перетоков буфер→очередь нет |

## Часть II. Стратегическая фаза (фазы 6–13, ТЗ v0.02)

ТЗ v0.02 меняет жанр: вместо одного корабля — флотилия сущностей под общим
потоком ОВМ, вместо очереди — «Приказы» по сущностям, добавляются стартовое
ограничение сектором с выходом через Цепь Миров, База Знаний с технологиями и
опциональный локальный ИИ-ассистент. Архитектурные решения и деривации от
буквы ТЗ разложены по фазам в `docs/Strategy - Plan.md` (блоки «Итог» после
каждой фазы) — здесь то же самое, но организовано «как это работает», а не
«что решили по ходу».

Мир существующих (MVP) игроков вайпнут миграцией `0003_entities` — обратной
совместимости с однокорабельным состоянием намеренно нет.

### Фаза 6 — сервер: флотилия и по-сущностные очереди

**Модель сущности.** `ships` (один корабль на игрока) заменена на `entities`
([server/src/db/schema.ts](server/src/db/schema.ts)) — и корабли, и
стационарные объекты (врата) одной таблицей, разница — в
`ENTITY_CLASSES[classId].mobile` из
[packages/shared/src/entities.ts](packages/shared/src/entities.ts). `queues`
получила `entity_id`, PK стал `(entity_id, slot)` вместо `(player_id, slot)`;
`cargo` тоже привязан к сущности — добыча физически локализована координатами
сущности, а не игрока. Миграция `0003_entities.sql` создаёт `entities` и
бэкфиллит по одной записи на игрока из `ships` (класс `scout_mk1`, имя
«БОРТ-001»), следующая (`0004_drop_ships`) убирает старую таблицу.

**Каскад ОВМ по флоту.** Один поток на N очередей — строгий приоритет
`(priority, id)`, не round-robin: `applyOvm` ([server/src/game/queue.ts](server/src/game/queue.ts))
итерирует сущности по приоритету, `pumpEntityQueue` — тело бывшего
одноочередного цикла на одну сущность; остаток каскадом уходит следующей,
финальный остаток — в общий буфер. При N=1 поведение бит-в-бит совпадает с
MVP (весь `queue.test.ts` перенесён без правок логики — только транспорт
сменился на `/orders/*` в фазе 8). Сущность в кулдауне **пропускается**, а не
обрывает каскад — иначе один кулдаун морозил бы весь флот.

**Домашний сектор.** `pickHomeSector(createRng(playerId + galaxySeed))`
([server/src/routes/auth.ts](server/src/routes/auth.ts)) — псевдослучайный
сектор на игрока в увеличенной галактике 32×32 (было 10×10); колонка
`players.home_sector_id` — якорь для Цепи Миров (фаза 11).

**API.** `POST /orders/add|remove|reorder` принимают `entityId`;
`POST /fleet/priority`, `POST /fleet/rename` — новые.

**Тесты** — `server/test/fleet.test.ts`: каскад по двум сущностям, кулдаун
одной не морозит вторую, приоритет соблюдается, поведение при N=1 совпадает с
MVP.

### Фаза 7 — клиент: каркас и «Флотилия»

**Снятие тройного хардкода.** До этой фазы список экранов был продублирован в
union-типе `Screen`, массиве `MENU` и цепочке `{#if}` в `App.svelte` —
добавление экрана требовало трёх согласованных правок. Теперь единственный
источник — [client/src/lib/screens.ts](client/src/lib/screens.ts): массив
`{id, key, label, component}`, из которого выводятся и меню, и хоткеи
(`1`..`9`, затем `0`), и сам компонент; `App.svelte` рендерит `SCREENS`
целиком, добавление экрана — одна строка (см. фазы 10 и 12, где так и
случилось).

**Фикс блокировки клавиатуры.** Обработчик клавиш в `App.svelte` был
зарегистрирован раньше экранных, поэтому `stopPropagation` из экрана его не
останавливал — ввод цифры в текстовое поле переключал экран. Геттер
`game.keysCaptured` ([client/src/lib/game.svelte.ts](client/src/lib/game.svelte.ts))
проверяет `document.activeElement instanceof HTMLInputElement/HTMLTextAreaElement`
**на лету**, а не через сохранённый флаг — булев флаг `inputFocused` в первой
версии однажды залип и намертво погасил клавиатуру; проверка по факту
рассинхронизироваться не может. Все глобальные обработчики (`App.svelte`,
`Tree.svelte`, экраны с хоткеями) гейтятся `!game.keysCaptured`.

**Общие компоненты** — `client/src/lib/terminal/`: `Overlay.svelte` (модалка,
сама считает `game.modalDepth`), `Confirm.svelte` (подтверждение, `Enter/Y` —
да, `Esc/N` — нет), `ListPicker.svelte` (выбор из списка с `disabled`/`note`
на пункт). `Tree.svelte` — плоская клавиатурная навигация по дереву,
добавлен в фазе 8, где у него появился первый реальный потребитель.

**«Флотилия»** — [client/src/screens/Fleet.svelte](client/src/screens/Fleet.svelte):
список сущностей (название/класс/статус/координаты), панель информации по
наведению или курсору (`$derived infoObject` с фолбэком), приказ прямо из
списка, приоритет `[+/-]`, переименование `[R]`.

### Фаза 8 — раздел «Приказы»

Очередь одного корабля становится инструментом управления флотилией (ТЗ
v0.02 п. 3). `game/orders.ts` ([server/src/game/orders.ts](server/src/game/orders.ts)) —
новый слой поверх `validateAction`, а не параллельная копия правил: третий
режим валидации `'offer'` (общие условия без конкретной цели) гарантирует,
что список «доступно» никогда не разойдётся с тем, что реально примет
`POST /orders/add`. Ключевой инвариант: `listOrders` сверяет заполненность
очереди (`orderSlots`) отдельно от `validateAction`, так как последняя этого
не проверяет.

`GET /orders/available[?entityId=]` отдаёт на каждую сущность массив
`OrderOption {action, costOvm, available, reason, target, candidates?}` —
`target='object'` дополнительно даёт список реальных кандидатов рядом
(объекты, известные игроку сканированием, в радиусе `nearDistance`).

**Клиент** — [client/src/screens/Orders.svelte](client/src/screens/Orders.svelte)
на `Tree.svelte`: узел-сущность (статус-бар готовности) → слоты приказов →
«ДОСТУПНЫЕ ПРИКАЗЫ» → свёрнутый затенённый узел «НЕДОСТУПНЫЕ (k)» с причиной
на каждый. Групповой приказ — веерная рассылка: `POST /orders/add` с
`entityIds[]`, каждая сущность валидируется независимо, часть могла
отклониться без блокировки остальных (`results: {entityId, ok, reason?}[]`).
`Queue.svelte` и алиасы `routes/queue.ts` удалены; deprecated-поля
`StateResponse` (`ship`/`queue`/`cargo`) убраны — `Cargo.svelte`/`Status.svelte`
переведены на сущность.

**Тесты** — `orders.test.ts`: недоступные цели без сканирования, появление
кандидата после подлёта, отказ всей очереди при заполнении слотов,
неподвижный класс не предлагает `move`, фильтр по `entityId`, весь флот без
фильтра — старый `queue.test.ts` перенесён на новый транспорт без изменения
движковых инвариантов.

### Фаза 9 — классы, модули, взаимодействие, минимальная боёвка

`interact`, `attack`, `special` перестают быть заглушками (ТЗ v0.02 п. 3.2).
`MODULES` ([packages/shared/src/entities.ts](packages/shared/src/entities.ts)) —
`mining_laser`/`railgun`/`refinery`/`survey_array` с полями `grants: ActionType[]`
и (для оружия) `damage`; `hasModuleGranting(entity, action)`
([server/src/game/entities.ts](server/src/game/entities.ts)) — гейт
«есть ли модуль» проверяется **до** поиска кандидатов в `game/orders.ts`,
иначе безмодульная сущность рядом с целью увидела бы «НЕТ РЕСУРСА РЯДОМ»
вместо честного «НЕТ МОДУЛЯ».

| Приказ | Условие | Результат |
|---|---|---|
| `interact` | станция/врата в радиусе `nearDistance` | сам решает стыковку/расстыковку по текущему `dockedObjectId` — свободный `/ship/undock` из MVP удалён, это больше не отдельная операция |
| `attack` | модуль с `damage`, `sameCoords`, `props.attackable` | урон вычитается из `props.hp`; на нуле — уничтожение и контейнер с точным лутом (переиспользует `pickup`) |
| `special` | модуль с `grants:['special']` | работает полноценно, но честно недоступен всем классам — ни один модуль пока не даёт `special` (это резерв из ТЗ, не заглушка в коде) |

`hp`/`hp_max` заводятся на всех сущностях сразу (миграция `0004_entity_hp`);
PvP и ответный огонь явно отложены — боёвка одиночная, детерминированная, без
NPC-ответа (развязка ToDo из ТЗ, см. `Strategy - Plan.md`, Часть III).

**Найденный и исправленный при проверке баг слияния конфига**: устаревшая
строка `game_config.actionCosts` в БД (сохранённая до переименования
`jump_local→move`) целиком перекрывала дефолт при мягком слиянии
`{...defaults, ...stored}` — новые ключи (`move`, `attack`, `special`) читались
как `undefined`. Исправлено точечным deep-merge вложенных объектов
(`actionCosts`/`conversion`/`limits`) в `mergeGameConfig`
([server/src/game/config.ts](server/src/game/config.ts)) — верхнеуровневые
плоские поля по-прежнему сливаются мелко, это осознанно (см. Фазу 13).

### Фаза 10 — База Знаний и Технологии

Контент — статичный каталог в
[packages/shared/src/knowledge.ts](packages/shared/src/knowledge.ts)
(`KNOWLEDGE_ENTRIES`, `TECHS` трёх веток nav/ind/def), в БД только прогресс
игрока: `player_knowledge`, `player_tech` (миграция `0005_knowledge.sql`).
Единый плагин-пойнт `Capability = {kind:'order'|'module'|'class'|'build', ...}`
описывает, что открывает технология — читают `game/orders.ts` (доступность) и
`game/actions.ts` (проверка при исполнении); реально гейтит движок пока
только `def.weapons` → `attack`, остальные — честный рабочий резерв (полный
цикл исследования есть, `unlocks` не подключены к проверкам, ровно как
`special` в фазе 9).

**Загрузка данных** — приказ `upload_data`: сервер сам находит в трюме
сущности контейнер `props.contents==='data-core'` (worldgen уже такие
генерировал, добавлен лишь детерминированный `props.entryId`) и открывает
запись `unlockEntry` ([server/src/game/knowledge.ts](server/src/game/knowledge.ts)).
`ActionParams` не пришлось трогать — приказ не принимает `objectId`.

**Исследование технологии** — НЕ приказ флоту, а мгновенное действие
интерфейса управления: `POST /tech/research`
([server/src/routes/knowledge.ts](server/src/routes/knowledge.ts)) списывает
`dataCost.ovm` из общего буфера напрямую внутри `lockPlayer`-транзакции, минуя
очередь приказов — тот же паттерн переиспользован в фазе 12 для оплаты
запроса ассистента.

**Клиент** — [client/src/screens/Knowledge.svelte](client/src/screens/Knowledge.svelte)
на `Tree.svelte`: подраздел «Записи» с поиском по строке (ТЗ v0.02 п. 5) и
«Технологии» — изученные (✓, ветка и описание при наведении) плюс доступные к
изучению, с причиной, если чего-то не хватает (`missingRequires`/
`missingEntries`/буфер).

### Фаза 11 — стартовые ограничения, врата, Цепь Миров

Реализует ТЗ v0.02 п. 4: новый игрок заперт в своём псевдослучайном секторе
(домашнем, из фазы 6), пока не изучит гиперпрыжок и не построит врата.

**Модель графа** — [server/src/game/chain.ts](server/src/game/chain.ts):
`sector_links` — рёбра **неориентированные и общие для всех игроков**
(топология Цепи не скрыта, в отличие от содержимого секторов), хранятся с
канонической парой `a<b` лексикографически, иначе `(a,b)` и `(b,a)` считались
бы разными рёбрами. `chain_keys` — точка монетизации (ТЗ п. 4): нулевой
`targetSectorId` значит «в случайный уже подключённый мир», конкретный сектор
выбирается при применении, не при выдаче.

**Приказ `build_gate`** стоимостью 250 000 ОВМ — **намеренно больше**
`ovmBufferCap` (100 000): врата нельзя купить из буфера, только накопить в
счётчике самого приказа за много сессий — движок каскада это уже умел, менять
было нечего. Постройка первых врат в мире не подключает ничего (`joinChainOnGateBuilt`
возвращает `null` — «первый узел Цепи»); вторые и далее — автоматически
подключаются к случайно выбранному уже существующему узлу через
`Math.random()` (намеренно НЕ через сидированный `createRng` — это разовое
игровое событие, не воспроизводимая генерация мира).

**`jump_hyper`** ([server/src/game/actions.ts](server/src/game/actions.ts))
требует одновременно: технологию `nav.hyperjump`, свои врата в ТЕКУЩЕМ
секторе (проверяется сразу на постановке приказа, не только на активации —
иначе «недоступно» пришлось бы узнавать через НЕВЫПОЛНИМО в очереди) и ребро
в `sector_links` до сектора назначения (проверяется на активации, как раньше
координаты). Старая проверка соседства секторов (`sectorsAdjacent`) удалена
из правил перемещения полностью.

**`POST /chain/connect`** применяется к **домашнему сектору игрока**, а не к
текущей позиции ведущей сущности — однозначно даже если игрок потом построит
врата ещё где-то; требует своих врат в домашнем секторе.

**Клиент** — [client/src/screens/GalaxyMap.svelte](client/src/screens/GalaxyMap.svelte)
рисует связанные Цепью сектора (`◆`) поверх сетки посещённых, легенда и
достижимость (`galaxy.reachable`, вычисляется сервером в
[server/src/routes/map.ts](server/src/routes/map.ts) через BFS по всем
`sector_links`); панель ключей Цепи Миров с «ПРИМЕНИТЬ» на неиспользованный
ключ и дебаг-кнопкой выдачи ключа.

### Фаза 12 — ИИ-ассистент (опционально, ТЗ v0.02 п. 7)

Игра полностью работоспособна без этой фазы — критерий явно требует честного
сообщения об отсутствии модели, а не деградации остального интерфейса.

**Разделение авторитетности.** Сервер — единственный источник того, что
ассистенту разрешено «знать» и сколько это стоит:
`POST /assistant/prepare` ([server/src/routes/assistant.ts](server/src/routes/assistant.ts))
списывает `assistantCostOvm` (300) из буфера **при каждом вызове** (не
одноразовая покупка, как исследование технологии) и отдаёт только реально
открытые игроком записи Базы Знаний — той же функцией `unlockedEntryIds`, что
и `GET /knowledge`. Сам разговор с моделью и её ответ сервер не видит вовсе —
это целиком клиент.

**Транспорт до Ollama.** В собранном Tauri-приложении webview — отдельный
origin, прямой `fetch()` упёрся бы в CORS без ручной настройки
`OLLAMA_ORIGINS`; вместо этого — `@tauri-apps/plugin-http`
([client/src-tauri/src/lib.rs](client/src-tauri/src/lib.rs):
`.plugin(tauri_plugin_http::init())`, permission `http:default` со scope на
`localhost`/`127.0.0.1` в `capabilities/default.json`), запрос реально уходит
из Rust. В браузерной сборке — обычный `fetch` (тот же путь, что и у
остального API). Единственная точка развилки —
`httpFetch` в [client/src/lib/assistant.svelte.ts](client/src/lib/assistant.svelte.ts).

**Замкнутая схема действий.** Вместо отдельной JSON-схемы/`zod` (в проекте не
используется нигде) — два OpenAI-совместимых tool'а, `issue_order` и
`research_tech`; `resolveToolCall` сверяет аргументы модели с тем же
`GET /orders/available`/`GET /tech`/`galaxy.reachable`, что видит обычный UI —
модель физически не может предложить несуществующую сущность, приказ или
цель, а свободный текст (не оформленный как вызов функции) никогда не
исполняется, только показывается репликой чата. Исполнение подтверждённого
вызова идёт через уже существующие `game.enqueue`/`api.techResearch`, не
отдельный привилегированный путь.

**Без стриминга** (сознательное отклонение от изначального наброска):
стриминг у OpenAI-совместимого API означает склейку
`tool_calls[].function.arguments` по чанкам, а именно tool-call — ядро фичи по
ТЗ, не просто чат; обычный ответ надёжнее.

**Живая калибровка с реальной моделью** (`qwen2.5:3b` через Ollama) вскрыла и
позволила исправить до сдачи фазы: `POST /assistant/prepare` без тела ловил
400 от Fastify (JSON `Content-Type` с пустым телом) — отправляется `'{}'`;
пример-заготовка в описании tool-схемы заставлял модель копировать сам
пример вместо чтения реальной сводки флота — переписано без конкретного
копируемого литерала; мелкая локальная модель иногда транслитерирует
кириллические имена латиницей (БОРТ-002 → BORT-002) — добавлено резервное
сопоставление по фонетическому «скелету» в `findEntityByName`.

### Фаза 13 — надёжность, баланс, полировка

**Hot-reload конфига** уже был общим механизмом с MVP (`setInterval` в
[server/src/index.ts](server/src/index.ts) перечитывает `game_config` раз в
60 с) — новые плоские поля вроде `assistantCostOvm` подхватываются мягким
слиянием `{...defaults, ...stored}` без единой правки кода; отдельного
внимания требуют только вложенные объекты (`actionCosts` и т.п., см. Фазу 9),
это уже покрыто `config.test.ts`.

**`server/scripts/wipe.ts`** — сброс мира, **не трогая** `credit_ledger`
(монотонность `packetSeq` важна для дедупликации коннектора) и `game_config`
(операционная калибровка, не состояние мира). Нетривиальная находка при
разработке: `TRUNCATE players CASCADE` в Postgres каскадирует в
`credit_ledger` **независимо** от объявленного `ON DELETE` у FK — это
особенность именно `TRUNCATE ... CASCADE`, не `DELETE`, — то есть исходная
версия скрипта молча стёрла бы ledger вместе с игроками. Единственный способ
сохранить ledger при живой FK-связи на `players.id` — не удалять строки
`players` вовсе, а сбрасывать их мутируемые игровые поля (`ovm_buffer`,
`home_sector_id`) через `UPDATE`.

**Нагрузочная проверка** (`server/test/load.test.ts`) — 10 сущностей одного
игрока, все с готовыми к довершению задачами; один вызов
`sweepQueueCompletions` должен довершить все 10 и уложиться в разумный
бюджет времени. Это страховка от будущей O(n²)-регрессии в `applyOvm`
(который и так делает до `fleet.length+2` проходов по всему флоту на каждый
вызов), а не тест абсолютной скорости железа.

**Проверка переживания рестартов** (`server/test/restart.test.ts`) — то, что
в MVP (Фаза 5) проверялось архитектурным рассуждением и ручным kill/restart
коннектора, для новых таблиц фаз 6–12 проверяется автоматически: приказ
останавливается на промежуточном прогрессе, первый процесс `buildApp()`
закрывается, поверх **той же** БД без пересоздания поднимается второй —
состояние (включая `player_knowledge`/`player_tech`/`sector_links`/
`chain_keys`) сверяется побитово, а повтор того же `packetSeq` после
«рестарта» подтверждает, что идемпотентность `credit_ledger` переживает смену
процесса.

**Аудит EN-переводов** — сверка каждого литерала внутри `t(...)` по всему
клиенту плюс отдельно значений `ACTION_LABELS`/`STATUS_LABELS`/`BRANCH_LABELS`
и реальных строк `reason` из `game/actions.ts`/`game/orders.ts` (не только
по логам постфактум) нашла и закрыла два класса пропусков в
[client/src/lib/i18n.svelte.ts](client/src/lib/i18n.svelte.ts): короткую форму
пункта меню «БАЗА ЗНАНИЙ» (был перевод только полного «БАЗА ЗНАНИЙ И
ТЕХНОЛОГИИ») и 19 причин недоступности приказов из фаз 6–9 (`ОЧЕРЕДЬ
ЗАПОЛНЕНА`, `СУЩНОСТЬ НЕПОДВИЖНА`, `ЦЕЛЬ НЕУЯЗВИМА` и т.п.), которые никогда
не попадали в словарь. Ни `tsc`, ни `vitest` такие пропуски не ловят — только
сверка строк вручную.
