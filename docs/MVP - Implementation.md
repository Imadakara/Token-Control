# Token Control — документация реализации (фазы 1–13)

Этот документ рассказывает, **как устроена игра изнутри** — не только «какой
файл за что отвечает», но и почему решения приняты именно так, какие
проблемы это решало и что оказалось неочевидным при реализации. Он написан
как сопроводительный рассказ к коду, а не как справочник API — если нужна
just-the-facts версия, читайте сам код по указанным путям.

Документ разбит на две части. **Часть I** описывает фазы 1–5 — тот самый
MVP по первой версии техзадания («ТЗ - MVP - Token Control v0.01.md»): один
корабль, одна очередь задач, семь экранов терминала. Здесь заложена вся
несущая архитектура — сервер как единственный источник истины, конвертация
токенов Claude Code в игровую валюту, устойчивость к рестартам. **Часть II**
описывает фазы 6–13 — вторую волну разработки по обновлённому техзаданию
(«ТЗ - MVP - Token Control v0.02.md», см. также `docs/Strategy - Plan.md`),
которая полностью сменила жанр игры: вместо одного корабля — целая флотилия
сущностей под общим потоком вычислительной мощности, вместо простой очереди —
раздел «Приказы», плюс стартовое ограничение одним сектором с выходом через
Цепь Миров, База Знаний с деревом технологий и опциональный локальный
ИИ-ассистент. Ссылки на пункты техзадания даны как «ТЗ п. N» (первая версия)
и «ТЗ v0.02 п. N» (вторая).

Обновлено: 2026-07-19. Состояние: фазы 0–13 полностью реализованы и
проверены (включая фазу 12 — «Ассистент», которая по ТЗ помечена
опциональной, и её позднейшее дополнение — встроенный движок Ollama для
дистрибуции через Steam, о нём в конце раздела Фазы 12). Фазы 14–98
зарезервированы под дальнейший roadmap ТЗ v0.02 (производство кораблей,
постройки, торговля между игроками) и не начаты. Фаза 99 (полноценная Steam
монетизация) тоже не начата.

## Часть I. MVP (фазы 1–5, ТЗ v0.01)

## Общая картина

Прежде чем нырять в отдельные фазы, стоит понять общую форму системы —
дальше всё остальное будет укладываться в неё.

```
┌────────────────────── клиент (Tauri) ──────────────────────┐
│  веб-UI (Svelte 5)          Rust-коннектор                 │
│  7 экранов терминала        ~/.claude/projects/**/*.jsonl  │
│  очередь, карты, трюм       парсинг → дедуп → ОВМ → outbox │
│        │  HTTP/WS                 │ HTTP (только числа)    │
└────────┼──────────────────────────┼────────────────────────┘
         ▼                          ▼
┌──────────────────── сервер (Node/Fastify) ─────────────────┐
│  авторитетная симуляция: очередь, действия, мир, лимиты    │
│  PostgreSQL (Drizzle): 11 таблиц, весь прогресс в БД       │
└────────────────────────────────────────────────────────────┘
```

Игра устроена как классическое клиент-серверное приложение, а не как
локальная программа, которая сама себе на слово верит. Внутри Tauri-окна
живут две почти независимые части: веб-интерфейс терминала на Svelte
(то, что видит игрок) и отдельный Rust-процесс — коннектор, который читает
логи Claude Code на диске игрока и превращает их в очки вычислительной
мощности (ОВМ). Обе части общаются с сервером по сети, как будто сервер
стоит где-то далеко — потому что в перспективе он действительно может стоять
далеко: игра спроектирована так, чтобы сервер можно было унести на реальный
хостинг, а клиент раздавать через Steam, ничего принципиально не меняя.

Три принципа выдержаны абсолютно во всех тринадцати фазах и объясняют
большинство решений ниже:

- **Сервер — единственный источник истины** (ТЗ п. 3.2). Клиент никогда не
  меняет игровое состояние сам по себе — он только просит сервер что-то
  сделать (HTTP-запросом), а сервер решает, разрешено ли это, и применяет
  изменение внутри транзакции PostgreSQL. У сервера при этом нет вообще
  никакого игрового состояния в оперативной памяти процесса — всё лежит в
  базе данных. Это значит, что рестарт сервера (упал, перезапустили,
  выкатили новую версию) ничего не стоит игроку: как только процесс
  поднимется заново, он прочитает из базы ровно то же состояние, на котором
  всё остановилось.
- **Всё, что можно калибровать, лежит в БД, а не зашито в код** (ТЗ п. 12.2).
  Стоимости приказов, формула конвертации токенов в ОВМ, антиабузные лимиты,
  параметры генерации мира — всё это строки в таблице `game_config`, которые
  сервер перечитывает без перезапуска (см. Фазу 5). Поменять баланс игры —
  значит выполнить `UPDATE` в базе, а не выкатить новую версию клиента.
- **Приватность по умолчанию** (ТЗ п. 10). Rust-коннектор, который читает
  файлы логов Claude Code на диске игрока, физически умеет доставать из них
  только числа расхода токенов и идентификаторы записей — структура, в
  которую парсится JSON, не содержит поля для текста сообщений вообще. На
  сервер в принципе не может утечь ни одна фраза из переписки с Claude Code.

## Фаза 1 — сервер: база данных, генерация мира, первые API-снапшоты

Первая фаза — это фундамент, на котором держится всё остальное: схема базы
данных, детерминированная генерация игрового мира и первые эндпоинты, по
которым клиент вообще может узнать, что происходит в игре.

### Схема БД — `server/src/db/schema.ts`

Вся схема описана через Drizzle ORM прямо в TypeScript (не в отдельном
`.sql`-файле), поэтому типы таблиц автоматически совпадают с типами, которые
использует остальной код сервера — рассинхронизация между «что реально в
базе» и «что думает код» структурно невозможна.

| Таблица | Назначение | Ключевые детали |
|---|---|---|
| `players` | игроки | `id` в формате `dev:<имя>` (в проде станет `steam:<id>`); `steam_id` — уникальная nullable-колонка, заранее подготовленная под будущую Steam-авторизацию; `ovm_buffer numeric(14,3)` — общий системный буфер очков вычислительной мощности (ТЗ п. 5) |
| `ships` | корабли | В MVP на игрока — ровно один корабль, поэтому первичный ключ таблицы — сам `player_id`; хранит `sector_id`, `x`, `y` (текущие координаты) и `docked_object_id` (к чему пристыкован, если пристыкован) |
| `queues` | очередь задач | Первичный ключ — пара (`player_id`, `slot`), слоты 1–3; `cost_ovm` и `progress_ovm` — сколько нужно и сколько уже накоплено; `status` — waiting/active; `activated_at` — момент, когда задача стала активной (нужен для отсчёта кулдауна перед фактическим исполнением) |
| `sectors` | сгенерированные сектора | `id` в формате `"gx:gy"`; строка появляется в первый момент, когда кто-то реально посещает сектор — генерация мира ленивая, не заранее |
| `objects` | объекты внутри секторов | `type` — станция/астероид/контейнер/феномен; `props jsonb` хранит скрытые от игрока свойства, которые раскрываются только анализом; `resource_amount`/`max_resource`/`respawn_at` отвечают за регенерацию ресурсов |
| `known_objects` | что именно игрок уже узнал об объекте | Первичный ключ (`player_id`, `object_id`); `level` — scanned либо analyzed (по ТЗ скан даёт только позицию, а анализ — полные свойства) |
| `visited_sectors` | какие сектора игрок уже посещал | Нужна для отрисовки карты галактики (ТЗ п. 4.2.3) — какие клетки сетки уже «открыты» |
| `cargo` | трюм корабля | `kind` — ресурс или подобранный объект; `item_type`, `qty`, `props` |
| `action_log` | журнал операций | `action`, `result` (готовая строка для терминала), `details jsonb` |
| `credit_ledger` | входящие пакеты ОВМ от коннектора | Ограничение **UNIQUE(`player_id`, `packet_seq`)** — это и есть фундамент идемпотентности всей системы начислений; хранит отдельно `ovm_submitted` и `ovm_accepted` плюс разбивку токенов по типам — эти цифры со временем накапливаются и становятся материалом для калибровки формулы (ТЗ п. 13.1) |
| `game_config` | серверный конфиг | Пары ключ/значение в формате jsonb: ключи `game` (баланс) и `world` (параметры генерации) |

Миграции генерируются автоматически через `drizzle-kit generate` (итоговый
SQL лежит в `src/db/migrations/`) и применяются как при старте настоящего
сервера, так и в начале каждого тестового прогона (`db/migrate.ts`). Уже на
этой ранней стадии в истории миграций видно, что схема живая: `0000_init` —
исходная схема, `0001_packet_seq_bigint` — пришлось расширить тип
`packet_seq` до `bigint`, когда стало ясно, что `int` может переполниться,
`0002_queue_activated_at` — добавление колонки с ручным бэкфиллом (`now()`
для уже активных на тот момент задач, чтобы свип их не «потерял» из-за
отсутствующей временной метки).

### Детерминированная генерация мира — `game/rng.ts`, `game/worldgen.ts`, `game/world.ts`

Мир не хранится целиком заранее «нарисованным» — вместо этого он
генерируется по формуле из строкового сида, и одна и та же комбинация сида и
координат сектора всегда даёт одно и то же содержимое, на любой машине и в
любой момент времени. Механизм: строковый сид пропускается через хэш-функцию
`xmur3`, а результат используется как начальное состояние генератора
случайных чисел `mulberry32`. Сид конкретного сектора собирается как
`"<общий сид галактики>/<sectorId>"` — поэтому у каждого сектора детерминизм
свой, но весь мир в целом воспроизводим целиком (это отдельно проверяется
тестом: сгенерировать сектор дважды и сравнить результат побайтово).

Сама галактика — это сетка `galaxyWidth × galaxyHeight` (в MVP 10×10),
сектора адресуются строками вида `"gx:gy"`. Соседними для гиперпрыжка (ТЗ
п. 6.3) считаются сектора на манхэттенском расстоянии 1 — то есть можно
прыгнуть только на клетку вверх/вниз/влево/вправо, не по диагонали и не
дальше. Содержимое каждого отдельного сектора подчиняется вероятностным
правилам из ТЗ п. 8: не больше одной станции (шанс появления 60%), от 3 до 8
астероидов с рудой одного из трёх типов (ferrum/silicium/iridium, запас от 5
до 20 единиц), от 0 до 3 контейнеров и от 0 до 2 феноменов; все координаты
внутри сектора — в диапазоне ±1000.

Генерация при этом **ленивая**: функция `ensureSectorGenerated` создаёт
строку сектора и его объекты только в момент, когда кто-то туда впервые
реально попадает, а не заранее для всей галактики целиком. Здесь есть тонкий
момент с гонкой: что если два игрока одновременно первыми прилетают в один и
тот же ещё не существующий сектор? Решение — `INSERT ... ON CONFLICT DO
NOTHING` с `RETURNING`: реально вставить объекты сектора сможет только та
из двух параллельных транзакций, которая первой успела создать саму строку
сектора; вторая просто увидит, что сектор уже есть, и ничего не будет
дублировать.

### Авторизация (dev-заглушка) — `routes/auth.ts`

Полноценной Steam-авторизации в MVP ещё нет — вместо неё простой
`POST /auth/dev {playerId}` (с валидацией позывного по маске `[\w-]{1,64}`).
При самом первом входе под этим позывным сервер создаёт игрока и его первый
корабль в стартовом секторе `5:5` (в позиции 0:0), генерирует этот сектор и
сразу помечает его посещённым, а в ответ выдаёт JWT-токен (через
`@fastify/jwt`, внутри которого лежит только `{pid}`). Все остальные
маршруты сервера защищены проверкой этого токена через `app.authenticate`.
Настоящая Steam auth ticket-авторизация (ТЗ п. 3.1) встанет позже, в фазе 6,
на то же самое место в архитектуре — менять предстоит только реализацию
одного маршрута, не весь слой авторизации.

### Первые API-снапшоты

- `GET /state` возвращает `StateResponse` — корабль, его очередь задач, буфер
  ОВМ, содержимое трюма и его вместимость. Сборка этого снапшота вынесена в
  отдельную функцию `game/state.ts::buildState`, потому что она нужна не
  только этому маршруту: тот же снапшот собирают и обработчик очереди, и
  обработчик начислений, и WS-пуш при каждом изменении.
- `GET /map/sector` отдаёт только те объекты сектора, которые игрок уже
  открыл сканированием — при этом `props` (скрытые свойства) и
  `resource_amount` включаются в ответ **только** если объект дополнительно
  проанализирован (ТЗ п. 6.5) — просто увидеть объект на карте ещё не значит
  знать, что он собой представляет.
- `GET /map/galaxy` отдаёт размеры сетки, текущий сектор игрока и список уже
  посещённых секторов.
- `GET /config` отдаёт весь игровой конфиг — стоимости приказов, формулу
  начисления, лимиты. Он публичный, и его же читает Rust-коннектор, чтобы
  знать актуальные коэффициенты формулы конвертации.

### Конфиг — `game/config.ts`

Функция `loadServerConfig` читает из таблицы `game_config` ключи `game` и
`world`; если каких-то полей в сохранённой записи не хватает (например,
конфиг был сохранён до того, как в код добавили новое поле), недостающее
подставляется из дефолтов пакета `@tokencontrol/shared`
(`DEFAULT_GAME_CONFIG`) и из `worldgen.ts` (`DEFAULT_WORLD`). Слияние
устроено мягко — как `{...defaults, ...stored}` — специально для того, чтобы
добавление нового поля конфига в код не ломало уже существующие записи в
базе данных, сделанные до этого поля.

Дефолтные значения баланса в MVP: стоимости базовых действий — 10, 100, 250 и
1000 ОВМ в зависимости от типа (ТЗ п. 6); формула конвертации токенов —
`kCacheW=1`, `kCacheR=0.1`, `N=1000` (ТЗ п. 7.3); кап общего буфера — 100 000
ОВМ (ТЗ п. 5); антиабузные лимиты — 500 ОВМ в минуту, 10 000 в час, 100 000 в
сутки (ТЗ п. 9); вместимость трюма — 100; радиус «рядом с объектом» — 10
условных единиц; кулдаун перед фактическим исполнением набравшей стоимость
задачи — 3 секунды (`taskCooldownSec`).

## Фаза 2 — движок очереди, семь действий, приём начислений

Вторая фаза — это сердце игрового цикла: как задача попадает в очередь, как
в неё «вливаются» очки вычислительной мощности, когда она считается
исполненной, и что происходит, если условие для её исполнения перестало
выполняться. Здесь же — приём пакетов ОВМ от коннектора с защитой от
двойного начисления.

### Модель очереди — `game/queue.ts`

Очередь подчиняется семи инвариантам, напрямую следующим из ТЗ п. 5:

1. **Максимум три задачи в очереди**, слоты всегда компактны — то есть без
   «дыр»: если исполнилась задача в слоте 1, то задача из слота 2
   немедленно сдвигается на её место, а из слота 3 — на место второй.
2. **Слот 1 — единственный активный.** Только в него вливаются очки
   вычислительной мощности; задачи в слотах 2 и 3 просто ждут своей очереди.
3. Функция `promoteQueue` занимается уплотнением слотов и активацией головы
   очереди — прежде чем активировать задачу, она заново проверяет условие её
   выполнимости (и, если условие выполняется, проставляет `activated_at`).
   Если условие не выполняется — задача получает статус «НЕВЫПОЛНИМО»,
   попадает в журнал и удаляется, а цикл повторяется для следующей задачи в
   очереди (та тоже может оказаться невыполнимой, и так далее).
4. Функция `applyOvm(ovm)` реализует сам каскад начисления. Перед КАЖДОЙ
   тратой ОВМ голова очереди перепроверяется заново: если условие уже не
   выполняется, задача пропускается, а важная деталь — её уже накопленный
   прогресс **не сгорает**, а возвращается обратно в общий каскад и уходит
   следующей задаче. ОВМ реально теряются только при ручном удалении задачи
   игроком, никогда — просто потому, что условие перестало выполняться.
   Задача, которая набрала полную стоимость, при этом не исполняется
   мгновенно — она ждёт кулдаун (`taskCooldownSec`, по умолчанию 3 секунды)
   после момента активации, и довершает её отдельный серверный «свип»
   (`game/sweep.ts`, тикающий раз в секунду), который заодно пушит клиенту
   событие о завершении и свежий снапшот состояния по WebSocket. Если после
   завершения задачи остался излишек ОВМ, он каскадом уходит следующей
   задаче в очереди; если очередь вообще пуста — остаток оседает в общем
   буфере (с учётом капа — переполнение сверх капа просто игнорируется, не
   пропадает и не копится «в долг»).
5. При постановке новой задачи (`addTask`) она сразу же может получить
   «аванс»: если в общем буфере уже лежат накопленные ОВМ, часть из них
   немедленно «вливается» в счётчик прогресса новой задачи (авансовая сумма
   равна минимуму из размера буфера и стоимости задачи). Даже если этого
   аванса хватило ровно на всю стоимость, задача всё равно не исполняется
   мгновенно — она проходит тот же кулдаун, что и любая другая, просто
   клиент увидит, что прогресс-бар сразу заполнен, и анимирует заполнение
   визуально по метке `activatedAt`.
6. Удаление задачи из очереди игроком сжигает весь накопленный по ней
   прогресс безвозвратно (клиент запрашивает подтверждение перед этим
   действием) и оставляет запись в журнале.
7. Перестановка задач местами разрешена только между слотами 2 и 3 (слот 1
   как активный трогать нельзя) — технически реализована через временный
   слот 99, потому что первичный ключ таблицы не даёт напрямую поменять
   местами значения `slot` у двух строк без промежуточного шага.

События завершения или пропуска задачи (тип `QueueEvent`) не отправляются
клиенту сразу же, а сначала накапливаются в контексте текущей транзакции
(`ActionCtx.events`), и только после успешного коммита транзакции пушатся по
WebSocket как событие `journal` — клиент реагирует на это строкой в
терминале вида «ЗАДАЧА ВЫПОЛНЕНА: …» и обновлением экрана журнала.

Все операции с очередью выполняются внутри `db.transaction` с явной
блокировкой строки игрока (`SELECT ... FOR UPDATE` внутри `lockPlayer`) —
это единственная точка сериализации во всей системе: если два запроса от
одного и того же игрока (например, одновременная постановка задачи и приём
пакета ОВМ от коннектора) прилетают почти одновременно, база данных сама
гарантирует, что они обработаются строго по очереди, а не столкнутся друг с
другом посреди изменения состояния.

### Действия — `game/actions.ts`

Здесь принято решение, которое потом определило форму почти всей игровой
логики на много фаз вперёд — **два разных режима проверки условий** для
одного и того же действия:

- Режим `enqueue` (постановка в очередь) проверяет только статические
  условия: существует ли цель, корректны ли параметры, находится ли сектор в
  пределах галактики. Позиционные условия вроде «корабль должен находиться
  рядом с целью» здесь намеренно **не проверяются** — потому что иначе была
  бы невозможна логичная последовательность приказов вроде «прыжок к
  астероиду → анализ → добыча»: в момент постановки всей цепочки корабль
  ещё физически не находится рядом с астероидом, само условие «рядом»
  выполнит только первый приказ в цепочке, когда до него дойдёт очередь.
- Режим `activate` (при активации головы очереди, и затем повторно прямо
  перед фактическим исполнением) проверяет условие полностью, со всеми
  позиционными требованиями. Если проверка проваливается — задача получает
  статус «НЕВЫПОЛНИМО» и пропускается. Это ровно та семантика, которую
  описывает ТЗ п. 5: «условие перестало выполняться к моменту, когда задача
  стала активной».

Семь действий MVP и условия их выполнимости при активации:

| Действие | Условие (activate) | Параметр | Результат | Стоимость |
|---|---|---|---|---|
| scan | всегда выполнимо | — | все объекты текущего сектора становятся известны игроку на уровне scanned; если сектор ещё не сгенерирован, он догенерируется на лету | 10 |
| jump_local | если цель — объект, он должен быть в текущем секторе | точка или объект | корабль перемещается в точку/к объекту; если был пристыкован — автоматически расстыковывается | 100 |
| jump_hyper | целевой сектор должен быть соседним (манхэттенское расстояние 1) | сектор | корабль переносится в точку (0,0) целевого сектора; сектор генерируется при необходимости и помечается посещённым; автоотстыковка | 1000 |
| dock | станция должна быть в радиусе `nearDistance` | — | `docked_object_id` корабля становится равен ID станции | 10 |
| analyze | корабль должен быть рядом с объектом | объект | запись в `known_objects` повышается до уровня analyzed (или создаётся, если её не было) — раскрываются `props` и запасы ресурса | 100 |
| mine | рядом с объектом, у объекта есть запас, трюм не полон | объект | запас объекта уменьшается на единицу (если дошёл до нуля — выставляется `respawn_at` для будущей регенерации); в трюм добавляется единица соответствующего ресурса | 100 |
| pickup | рядом с контейнером, трюм не полон | объект | контейнер целиком перемещается в трюм как объект; ссылки на него из `known_objects` всех игроков удаляются, затем удаляется и сам объект из мира | 10 |

Расстыковка при этом мгновенна и абсолютно бесплатна (ТЗ п. 6.4) — это
отдельный вызов `POST /ship/undock`, который не проходит через очередь
задач вообще, потому что логически это не «действие корабля», а просто
переключатель состояния.

«Рядом с объектом» везде означает евклидово расстояние не больше
`nearDistance` (по умолчанию 10 условных единиц, задаётся конфигом). Прыжок
к объекту специально ставит корабль ровно в его координаты, а не рядом
приблизительно — это гарантирует, что следующее в очереди условие «рядом»
для анализа или добычи гарантированно выполнится, без зазора на ошибку
округления.

### Приём начислений — `game/credits.ts`

`POST /credits/submit {packetSeq, ovm, tokens, intervalStart, intervalEnd}` —
единственный вход, через который ОВМ вообще попадают в игру от
Rust-коннектора, и всё это происходит внутри одной транзакции:

1. `lockPlayer` (то же `SELECT ... FOR UPDATE`, что и в очереди) сериализует
   этот вызов с любыми параллельными командами игрока.
2. Проверка повтора: если пара (`player_id`, `packet_seq`) уже встречалась в
   `credit_ledger` раньше, сервер просто возвращает тот же самый результат
   (`{accepted, clipped}`), что вернул в первый раз, и **не начисляет ничего
   заново**. Это и есть идемпотентность (ТЗ п. 11) — если коннектор отправил
   пакет, но не дождался ответа из-за обрыва сети или рестарта и решил
   отправить его повторно, повторная отправка совершенно безопасна.
3. Антиабузная защита (ТЗ п. 9): по данным леджера считается сумма уже
   принятых ОВМ (`ovm_accepted`) в трёх скользящих окнах — минута, час,
   сутки; принимается `accepted = min(submitted, остаток самого узкого из
   трёх окон)`. Важно, что превышение лимита не отклоняется целиком и не
   ведёт ни к какому «бану» — просто излишек сверх лимита мягко урезается
   (поле `clipped` в ответе), а остальное честно засчитывается.
4. Пакет записывается в леджер целиком, отдельно храня и то, сколько было
   заявлено (`submitted`), и то, сколько реально принято (`accepted`) — эта
   разница сама по себе становится материалом для будущей калибровки формулы.
5. Наконец, принятая сумма проходит через уже знакомый `applyOvm(accepted)` —
   ровно тот же каскадный механизм, что используется и при постановке задачи
   с авансом из буфера.

После завершения транзакции маршрут дополнительно пушит клиенту свежий
`StateResponse` по WebSocket, чтобы интерфейс обновился без опроса.

### Регенерация ресурсов — `game/regen.ts`

Раз в 60 секунд по таймеру выполняется простой запрос: `UPDATE objects SET
resource_amount = max_resource, respawn_at = NULL WHERE respawn_at <= now()`.
Время, через которое истощённый астероид восстанавливается, задаётся
конфигом (`world.respawnMinutes`, по умолчанию 30 минут) и выставляется
именно в момент, когда добыча (`mine`) исчерпывает последнюю единицу
ресурса.

### WebSocket — `ws.ts`, `app.ts`

Подключение — `GET /ws?token=<jwt>`: токен передаётся в query-параметре, а
не в заголовке, потому что браузерный `WebSocket` API не умеет
пользовательские заголовки при установке соединения. Реестр `WsRegistry`
хранит множество активных сокетов на каждого игрока (у игрока может быть
открыто несколько вкладок/окон одновременно) и предоставляет два метода:
`push(pid, msg)` — отправить сообщение конкретному игроку, и `broadcast(msg)`
— отправить всем подключённым сразу (это понадобится позже, в фазе 5, для
рассылки уведомлений об изменении конфига). Типы сообщений, общие для
сервера и клиента, живут в shared-пакете: `state_delta` шлётся после каждой
мутации состояния, `config_changed` появится в фазе 5. Поскольку ТЗ п. 11
допускает задержку обновления интерфейса в 1–5 секунд, не было смысла
городить протокол дельт — сервер просто шлёт полный снапшот состояния
целиком при каждом изменении, и это оказалось вполне достаточно быстрым.

### Инструменты и тесты фазы

`scripts/feed.ts` — «фейковый коннектор»: авторизуется под указанным
позывным и шлёт синтетические пакеты ОВМ (используя `Date.now()` как
`packetSeq`). Он использовался для отладки движка до того, как в фазе 4
появился настоящий Rust-коннектор, и остаётся удобным инструментом для
проверки баланса вручную и сейчас.

Тестовый набор фазы (`server/test/*.test.ts`, на vitest, изначально 20
тестов) покрывает и детерминизм с граничными случаями генерации мира, и
базовые API (авторизация, снапшоты состояния, карты, конфиг), и — самое
важное — сценарии самого движка очереди: полный цикл
скан→прыжок→анализ→добыча от начала до конца, мгновенное исполнение задачи,
целиком закрытой авансом из буфера, переход в статус «НЕВЫПОЛНИМО» после
того, как корабль улетел от цели, сгорание прогресса при ручном удалении
задачи, перестановка слотов 2↔3, идемпотентность при повторной отправке
одного и того же пакета, урезание при превышении минутного лимита, кап
общего буфера в 100 000 ОВМ, и гиперпрыжок строго в соседний сектор, не
дальше. Тестовая база данных пересоздаётся заново на каждый тестовый файл
(`DROP/CREATE DATABASE tokencontrol_test`), поэтому файлы обязаны
выполняться строго последовательно, а не параллельно (это настроено через
`vitest.config.ts: fileParallelism: false`). HTTP-запросы в тестах не ходят
по реальной сети — используется `app.inject` от Fastify, который вызывает
обработчики маршрутов напрямую в памяти.

## Фаза 3 — терминальный интерфейс на Svelte 5

Третья фаза — это первый настоящий интерфейс игры: терминал в ретро-стиле
с семью экранами, полностью управляемый с клавиатуры.

### Архитектура клиента

`lib/api.ts` — типизированный HTTP-клиент поверх обычного `fetch`, где все
типы запросов и ответов приходят из общего пакета `@tokencontrol/shared`
(то есть сервер и клиент буквально используют одни и те же TypeScript-типы,
рассинхронизация исключена на уровне компиляции). JWT-токен хранится в
`localStorage`. Отдельная функция `connectWs` устанавливает WebSocket-
соединение с экспоненциальным переподключением при обрыве связи (задержка
растёт от 1 до 15 секунд).

`lib/game.svelte.ts` — единый реактивный стор, построенный на рунах Svelte 5
(поля `$state` внутри обычного класса вместо привычных Redux-подобных
хранилищ): здесь живёт состояние игры, конфиг, загруженные карты, журнал,
текущий открытый экран, режим выбора цели для приказа и строка сообщений
терминала внизу экрана. Обновляется это состояние двумя параллельными
путями — push-события `state_delta` по WebSocket и подстраховывающий опрос
сервера раз в 5 секунд (плюс тихое обновление карт после каждого нового
снапшота, на случай если что-то на карте изменилось). Показатель
«ОВМ/мин» в шапке — это не то, что реально считает сервер (сервер вообще не
хранит скорость потока), а клиентская оценка: разница накопленного объёма
(буфер плюс прогресс всех активных задач) между двумя последовательными
снапшотами, делённая на прошедшее время.

Постановка приказа (`chooseAction`) устроена по-разному в зависимости от
того, нужен ли приказу параметр. Приказы вроде скана или стыковки, которым
не нужна цель, отправляются на сервер сразу же. Приказы с параметром
(например, «прыжок к точке» или «анализ объекта») переключают клиент в
специальный «pick-режим» (`game.pick = {action, target}`) и одновременно
открывают подходящую для выбора карту — сектора или галактики. Нажатие Enter
на карте собирает итоговые параметры действия и отправляет запрос на
постановку в очередь; Esc в любой момент отменяет выбор — эта клавиша
обрабатывается глобально, в `App.svelte`.

### Семь экранов терминала (ТЗ п. 4.2)

| Экран | Клавиша | Что реализовано |
|---|---|---|
| Queue | 1 | Три слота очереди с ASCII-прогресс-барами вида `X/Y ОВМ`. Задача, набравшая полную стоимость, дополнительно анимирует заполнение бара в течение кулдауна перед фактическим исполнением — отдельный таймер на 100 мс включается только тогда, когда такая задача реально есть, чтобы не тратить ресурсы впустую. Клавиша [A] открывает меню доступных действий со стоимостями прямо из конфига, [D]/[Del] удаляет задачу с обязательным подтверждением (потому что прогресс по ней сгорит), [+]/[−] переставляет местами слоты 2 и 3, курсор — стрелками вверх/вниз. |
| SectorMap | 2 | Символьная ASCII-карта размером 61×21 клетку (`·` — пусто, `@` — свой корабль, `S`/`*`/`c`/`~` — станция/астероид/контейнер/феномен), с проекцией игровых координат в диапазоне ±1000 на эту сетку. Курсор двигается стрелками, [Tab] перебирает цели по порядку, а клик мышью обрабатывается одним делегированным обработчиком на весь `<pre>`-блок карты (координаты клетки читаются из `data-`атрибутов), а не тысячей отдельных кликабельных DOM-элементов — иначе карта размером 61×21 создавала бы больше тысячи кнопок. Справа — две панели одна над другой на всю высоту карты: список известных объектов (с отметкой `✓АНАЛИЗ`, если объект уже проанализирован) и подробная информация о том объекте, на который сейчас наведён курсор мыши или клавиатуры — тип, координаты, уровень знания о нём, а для уже проанализированных объектов ещё и раскрытые свойства с текущим запасом ресурса. |
| GalaxyMap | 3 | Сетка секторов 10×10: `▣` — сектор, где сейчас находится игрок, `▪` — уже посещённые сектора, `·` — ещё неизвестные. Этот экран также служит для выбора целевого сектора при постановке гиперпрыжка. Курсор сбрасывается на текущий сектор игрока только в момент открытия самого экрана (реализовано через `$effect`, зависящий от смены `game.screen`, при этом чтение самой карты внутри эффекта обёрнуто в `untrack` — иначе фоновое обновление карты каждые несколько секунд постоянно сбрасывало бы курсор туда, куда его не двигал сам игрок). |
| Cargo | 4 | Шкала заполненности трюма и таблица того, что в нём лежит — ресурсы и подобранные объекты отдельными строками. |
| Status | 5 | Текущий сектор и координаты корабля, статус стыковки (с возможностью расстыковаться клавишей [U]), полная информация о накопителе ОВМ (входящий поток, текущий буфер) и живой статус Rust-коннектора. |
| Journal | 6 | Лента записей из `action_log`, самые свежие сверху; строки со статусом «НЕВЫПОЛНИМО» подсвечены красным для наглядности. Обновляется и при открытии экрана, и мгновенно по WS-событиям о завершении задач. |
| Settings | 7 | Переключатель CRT-эффекта [C], переключатель языка RU/EN [E] (появится в фазе 5), информация о состоянии коннектора, смена позывного [L]. |

Строка сообщений терминала внизу экрана — отдельный, не привязанный к
конкретному экрану механизм: завершения и провалы задач приходят WS-пушем
типа `journal` и превращаются в короткие сообщения вида «ЗАДАЧА ВЫПОЛНЕНА:
…» или «НЕВЫПОЛНИМО: …», которые видны независимо от того, какой экран
сейчас открыт. Индикатор потока ОВМ/мин в шапке терминала специально
плавно затухает до нуля, если приток не обновлялся дольше 60 секунд —
это сделано, чтобы значение не «зависало» навсегда на последней ненулевой
цифре после того, как игрок закрыл Claude Code и агент перестал работать.

### Оболочка — `App.svelte`

Шапка терминала (ТЗ п. 4.3) показывает индикатор связи с сервером, текущий
входящий поток ОВМ в минуту и прогресс-бар активного слота очереди (либо,
если очередь пуста, сообщение о том, что весь приток идёт прямо в общий
буфер). Меню экранов переключается и цифрами от 1 до 7, и мышью. Вся
обработка клавиатуры в приложении завязана на один глобальный слушатель
`svelte:window onkeydown`, который сверяется с тем, какой экран сейчас
активен, прежде чем на что-то реагировать; отдельный модуль
`lib/terminal/keys.ts` нормализует устаревшие/легаси-названия клавиш вроде
`Down` в современный стандарт `ArrowDown`, чтобы не думать об этом различии
в каждом обработчике по отдельности.

### Стилистика (ТЗ п. 4.1)

Моноширинный шрифт, палитра из двух акцентных цветов — зелёный фосфор и
янтарь — задана через CSS-переменные в `app.css`, а вся псевдографика
рисуется внутри тегов `<pre>`. Эффект CRT-монитора — это один статичный
CSS-слой (`Crt.svelte`: повторяющийся градиент сканлайнов плюс лёгкая
виньетка по краям), который можно выключить в настройках; никаких анимаций
или canvas-рендеринга здесь нет специально — фоновая нагрузка на процессор
от этого эффекта практически нулевая.

### Верификация

Полный игровой цикл был пройден вручную в браузере против настоящего
сервера: вход под позывным → сканирование сектора (мгновенно закрывается из
буфера) → прыжок к астероиду → постановка в очередь пары «анализ, затем
добыча» → подача ОВМ извне → в трюме появляется единица `FERRUM`, статус и
журнал отражают это корректно; WS-пуш обновляет экран сам, без перезагрузки
страницы.

## Фаза 4 — коннектор Claude Code на Rust (внутри Tauri)

Четвёртая фаза добавляет то, что превращает игру из абстрактной песочницы в
инструмент, реально завязанный на работу с Claude Code: фоновый Rust-процесс,
который следит за файлами логов на диске и превращает реальный расход
токенов в игровую валюту.

### Поток данных целиком

```
~/.claude/projects/**/*.jsonl
  → рескан каждые 5 с (walkdir; размер файла больше сохранённого офсета?)
  → parser: дочитать с офсета ТОЛЬКО полные строки; type=="assistant" && usage
  → store (SQLite, одна транзакция на цикл):
      INSERT OR IGNORE в seen (дедуп) → только новые записи суммируются
      офсеты файлов обновляются
      T = in + out + kW·cache_w + kR·cache_r;  ОВМ = T/N + остаток
      пакет → outbox (packetSeq = AUTOINCREMENT)
  → submit: НЕМЕДЛЕННО при свежих токенах, иначе ретраи outbox каждые 15 с;
      пакет удаляется из outbox ТОЛЬКО после ack сервера
```

Статус агента («работает» он сейчас или нет) определяется не просто наличием
файлов логов, а тем, **вырос ли** хотя бы один из них за последние 120 секунд
(константа `ACTIVITY_WINDOW`) — в статус, который видит игрок, входит и то,
сколько секунд прошло с последней такой активности (`lastActivitySecs`).
Это важная деталь: в самой первой версии статус определялся просто по
наличию файлов на диске, и это давало вечное «ОБНАРУЖЕН», даже когда Claude
Code был давно закрыт — файлы-то никуда не делись, просто больше не растут.

### Модули коннектора — `client/src-tauri/src/connector/`

**`parser.rs`** отвечает за чтение файлов и разбор JSON. Структура, в
которую парсится каждая строка лога, содержит буквально только то, что
нужно для подсчёта: `type`, `uuid`, `requestId`, `message.model` и
`message.usage` с четырьмя числовыми полями расхода токенов — текстовое
содержимое сообщений просто физически негде оказаться, для него нет поля в
структуре (ТЗ п. 10). Записи, у которых `type` не равен `"assistant"`,
записи без блока usage и вовсе невалидный JSON молча пропускаются — на
живых логах Claude Code реально встречаются посторонние форматы записей, и
парсер должен их спокойно проглатывать, а не падать. Функция
`read_from_offset` продвигает сохранённый офсет чтения только за полностью
завершённые строки (то есть строки, после которых уже есть символ перевода
строки) — недописанная последняя строка файла (например, если Claude Code
как раз в этот момент дописывает лог) будет корректно дочитана уже на
следующем цикле, не раньше. Отдельно обрабатывается случай, когда
сохранённый офсет вдруг оказывается больше реального размера файла — это
значит, что файл был усечён или перезаписан заново, и тогда чтение просто
начинается с нуля.

**`store.rs`** — локальное хранилище коннектора на SQLite (через `rusqlite`,
в режиме WAL для надёжности при параллельном доступе). Здесь четыре сущности:
`file_offsets` — офсет чтения по каждому файлу; `seen` — **глобальный**
индекс уже засчитанных записей, ключом служит `requestId` (а если его нет —
`uuid` как запасной вариант); эта глобальность важна, потому что при
возобновлении или форке сессии Claude Code одни и те же записи иногда
дублируются в новых файлах — без глобального дедупа это привело бы к
повторному начислению за одну и ту же реально потраченную работу (ТЗ п. 7.2).
`outbox` — оффлайн-буфер ещё не подтверждённых сервером пакетов (ТЗ п. 3.2):
если сети нет или сервер недоступен, пакеты остаются здесь и переживают даже
перезапуск самого коннектора, удаляясь только после подтверждения от
сервера. `meta` хранит служебные вещи: `remainder` — дробный остаток ОВМ,
который не попал в предыдущий пакет из-за ограничения точности (точность
пакета — три знака после запятой, согласована с типом `numeric(14,3)` на
сервере), и `baseline_done` — флаг того, была ли уже выполнена начальная
индексация истории. Функция `commit_scan` выполняет весь цикл — дедуп,
обновление офсетов, конвертацию в ОВМ и формирование пакета — атомарно,
одной транзакцией: авария процесса ровно между двумя циклами сканирования
не может привести ни к потере уже посчитанных токенов, ни к их повторному
учёту.

**Базовая линия (baseline).** При самом первом запуске коннектора на новой
машине вся уже существующая история логов индексируется, но с флагом
`credit=false`: идентификаторы записей всё равно попадают в `seen` (чтобы
не засчитать их повторно позже), офсеты файлов сразу выставляются в конец
файла, но **начисления не происходит вообще**. Логика простая: игра не
должна задним числом наградить игрока за месяцы работы с Claude Code,
которая случилась ещё до установки игры — засчитывается только то, что
потрачено уже после установки.

**`submit.rs`** — блокирующий HTTP-клиент на `reqwest`. Он делает две вещи:
`GET /config` за коэффициентами формулы конвертации (это и есть та самая
серверная калибровка без обновления клиента из ТЗ п. 7.3 — коэффициенты
перечитываются заново на каждом цикле отправки, поэтому правка баланса на
сервере доходит до всех уже установленных коннекторов сама) и
`POST /credits/submit` с токеном авторизации в заголовке. Если сеть или
сервер недоступны, запрос просто проваливается, а пакет остаётся в outbox
до следующей попытки — никакой сложной логики повторов здесь не нужно,
её уже обеспечивает сама структура хранилища.

**`mod.rs`** — управляющий цикл, который крутится в отдельном обычном
Rust-потоке (не async), и статус коннектора (`ConnectorStatus`: активен ли
агент и сколько секунд назад, сколько файлов отслеживается, сколько записей
засчитано, что лежит в outbox, результат последней отправки, последняя
ошибка) отправляется в канал после каждого шага цикла. Здесь же принято
осознанное архитектурное решение — «рескан по таймеру, а не подписка на
файловые события операционной системы»: на Windows уведомления файловой
системы (`notify`-события) на практике ненадёжны, теряются или дублируются,
а простой периодический пересчёт размера файлов раз в 5 секунд надёжнее и
сам по себе служит источником истины, на который можно положиться. При этом
свежие токены отправляются на сервер немедленно, как только обнаружены,
поэтому реальная задержка между «агент поработал» и «ОВМ появились в игре»
— это единицы секунд, а не 5-секундный цикл сканирования сам по себе.

### Интеграция с приложением

В `lib.rs` определены две Tauri-команды: `connector_start(serverUrl, token)`
и `connector_stop`, а поток статусов ретранслируется в веб-интерфейс как
событие `connector-status`. Файл SQLite коннектора хранится в
`app_data_dir()/connector.sqlite` — в стандартной для приложения папке
данных, специфичной для операционной системы. На веб-стороне,
`lib/connector.svelte.ts` определяет, запущено ли приложение внутри Tauri
(проверкой наличия глобального объекта `__TAURI_INTERNALS__`) и в этом
случае динамически импортирует `@tauri-apps/api`, чтобы вызвать команду
запуска; `game.start()` делает это автоматически сразу после успешного
логина, передавая коннектору токен. В браузерной сборке (без Tauri-окна)
коннектор просто честно показывает статус «недоступен» — это ожидаемое,
а не ошибочное поведение. Отдельно есть `bin/connector_cli.rs` — тот же
самый цикл коннектора, но без графического окна вообще, запускаемый прямо
из терминала (`cargo run --bin connector_cli -- <player> [server]
[projectsDir]`) — удобно для отладки без запуска всего Tauri-приложения.

### Верификация

Девять cargo-тестов покрывают: разбор блока usage, пропуск чужих (не
assistant) записей, использование `uuid` как запасного идентификатора при
отсутствии `requestId`, корректную обработку недописанной последней строки
файла (офсет не должен продвинуться дальше последнего полного перевода
строки, а дочитывание на следующем цикле должно пройти без ошибок), усечение
файла, работу глобального дедупа, корректный перенос дробного остатка между
пакетами (проверено конкретным числовым примером: 0.5 + 0.501 в сумме дают
ровно 1.001, без потери точности), отсутствие начисления при baseline-
индексации и корректную обработку подтверждения от сервера.

Живая проверка на реальных логах: коннектор запущен против настоящей папки
`~/.claude/projects` с 32 файлами логов, успешно прошёл baseline-индексацию
и засчитал только свежие записи текущей на тот момент сессии Claude Code; в
леджере видно, что пакеты с расходом кэш-чтения порядка 310–390 тысяч
токенов конвертировались примерно в 32–41 ОВМ — то есть формула сходится
с ожиданиями. Отдельно проверен рестарт-сценарий: процесс коннектора
принудительно убит и запущен заново — начислилось только то, что реально
появилось в логах после рестарта, без повторного зачёта уже учтённой ранее
истории (буфер вырос с 162.3 до 261.1, ровно на новую порцию). И наконец, в
настоящем десктопном окне: игрок вошёл в игру, коннектор стартовал
автоматически сам, и буфер вырос с 40.1 до 121.9 ОВМ за примерно 90 секунд
реальной работы с агентом.

## Фаза 5 — надёжность и полировка MVP

Пятая фаза закрывает MVP-часть разработки: убедиться, что игра переживает
рестарты без потерь, добавить фоновый режим со сворачиванием в трей,
локализацию на два языка и возможность калибровать баланс без пересборки
клиента.

### Переживание рестартов (ТЗ п. 11)

Устойчивость к рестартам была заложена архитектурно ещё с первой фазы, и в
этой фазе она была целенаправленно проверена как отдельный критерий приёмки:
на сервере весь игровой прогресс лежит исключительно в PostgreSQL, все
мутации происходят внутри транзакций, и никакого игрового состояния в
оперативной памяти процесса не хранится вовсе. На клиенте — офсеты чтения
файлов, индекс дедупликации и оффлайн-очередь коннектора лежат в локальном
SQLite, а токен сессии — в `localStorage`; идемпотентность обработчика
`credits.submit` отдельно покрывает случай, когда коннектор отправил пакет,
не дождался ответа сервера из-за обрыва соединения, и на всякий случай
отправляет тот же самый пакет повторно.

### Трей и «тихий» фоновый режим (ТЗ п. 11) — `lib.rs`

Через Tauri-фичу `tray-icon` в системном трее появляется иконка приложения
с простым меню — «Показать терминал» и «Выход». Закрытие окна крестиком не
завершает приложение, а перехватывается обработчиком `CloseRequested`,
который вызывает `hide()` и `prevent_close()` — окно терминала сворачивается
в трей, но Rust-коннектор продолжает в фоне считать ОВМ как ни в чём не
бывало. Веб-часть интерфейса при этом реагирует на событие
`visibilitychange`: пока окно скрыто, она останавливает периодический опрос
сервера, а поскольку CRT-эффект и так статичен (без анимаций и canvas),
потребление ресурсов в таком «тихом» состоянии почти нулевое. Как только
окно снова показывается, происходит немедленное обновление состояния.

### Локализация RU+EN (ТЗ п. 11) — `lib/i18n.svelte.ts`

Устройство локализации намеренно простое: русские строки интерфейса сами
служат ключами словаря переводов — вызов вида `t('ОЧЕРЕДЬ')` в словаре
превращается в `'QUEUE'`. Это значит, что компоненты остаются читаемыми
прямо в исходном коде (видно сразу, что на экране появится русский текст,
а не абстрактный идентификатор строки), а весь англоязычный словарь
собран в одном файле (порядка сотни записей на момент фазы 5).
Переключение языка происходит на экране Настроек клавишей [E], выбор
сохраняется в `localStorage` и применяется реактивно — сама реализация
словаря это простой класс с руной `$state` внутри. Строки журнала операций,
приходящие с сервера, в MVP остаются исключительно русскими — они
воспринимаются как игровой контент, а не как элемент интерфейсного хрома,
и вынос их в клиентскую локализацию отдельно отмечен как будущая работа
(которая частично и была сделана — в фазе 13, когда обнаружился пробел в
переводе причин отказа в приказах).

### Живая калибровка конфига без перезапуска (ТЗ п. 12.2) — `server/src/index.ts`

Раз в 60 секунд сервер сам перечитывает таблицу `game_config`; если
содержимое изменилось по сравнению с тем, что уже загружено в память,
происходит `Object.assign` в уже используемый объект конфига (так все
маршруты сразу видят новые значения, без перезапуска процесса) и
дополнительно рассылается WS-событие `config_changed` всем подключённым в
данный момент клиентам — интерфейс обновляет отображаемые стоимости прямо
в меню действий без перезагрузки страницы. Итоговый эффект: чтобы поправить
баланс игры, достаточно выполнить `UPDATE game_config ...` прямо в базе
данных — ни новый релиз клиента, ни даже рестарт сервера для этого не
нужны.

### Запуск игры одной командой

Команда `npm run desktop` из корня проекта запускает `tauri dev` внутри
клиента, у которого `beforeDevCommand` настроен на скрипт
`scripts/dev-stack.mjs`. Этот скрипт сначала проверяет занятые порты и
действует по обстоятельствам: если весь dev-стек (сервер и vite) уже
работает — просто переиспользует его и открывает поверх только окно
Tauri; если работает только игровой сервер, но не веб-часть — доподнимает
один vite; если нужный порт занят посторонней программой — выдаёт понятную
текстовую ошибку вместо непонятного стектрейса из внутренностей vite; если
свободно всё — поднимает полный стек с нуля: сначала PostgreSQL через
`docker compose up -d db` (шаг `predev`), затем игровой сервер на порту
8787 и vite на порту 5173, и только после этого открывает окно. В Rust-
пакете два бинарных файла — само окно приложения и `connector_cli` для
отладки — поэтому в `Cargo.toml` явно указано `default-run = "app"`, чтобы
`cargo run` без уточнения знал, какой из двух запускать по умолчанию.
Отдельная деталь: сервер читает номер порта из переменной окружения
`GAME_SERVER_PORT`, а не из общепринятой `PORT` — потому что многие
превью-раннеры (окружения для предпросмотра/CI) сами подставляют `PORT` для
фронтенда, и использование того же имени переменной ломало бы выбор порта
сервера самым неожиданным образом.

## Отладочные инструменты MVP

- **Дебаг-режим.** Вход с позывным `DEBUG` открывает на экране Настроек
  отдельную панель «НАСТРОЙКИ — ОТЛАДКА» (клиент определяет это просто по
  сравнению `playerName` с фиксированной строкой). Единственная команда на
  этом этапе — `[B] +1000 ОВМ В БУФЕР`, которая вызывает `POST
  /debug/credit` и начисляет ОВМ напрямую в буфер, минуя и коннектор, и
  антиабузные лимиты, и леджер (кап общего буфера при этом всё равно
  соблюдается). Сервер пускает к любым дебаг-маршрутам только позывной
  `dev:DEBUG` — всем остальным отвечает 403, и это отдельно покрыто тестом.
- `server/scripts/feed.ts` — отправка синтетических пакетов ОВМ через
  обычный, ничем не привилегированный `credits/submit` (то есть с
  применением всех обычных лимитов) — удобно для проверки антиабузной
  защиты и калибровки баланса.
- `client/src-tauri/src/bin/connector_cli.rs` — тот же коннектор, что и
  внутри приложения, но без окна Tauri, печатающий статусы прямо в
  терминал: активность агента, состояние outbox, сколько принято и сколько
  урезано при последней отправке.

## Отступления от буквы ТЗ и осознанные упрощения

| Решение | Почему так |
|---|---|
| Проверка условий при постановке в очередь — только статическая | Иначе была бы невозможна логичная цепочка «прыжок к цели → действие у цели»: полная проверка сознательно перенесена на момент активации задачи, что соответствует духу ТЗ п. 5, даже если не букве |
| Рескан-таймер вместо подписки на файловые события ОС | Надёжнее на Windows, где notify-события на практике теряются; задержка до 10 секунд не имеет значения при батчах отправки в 30–60 секунд. Переход на watcher остаётся возможной будущей оптимизацией |
| Стоимость `jump_local` не масштабируется от дистанции прыжка | ТЗ прямо допускает такое масштабирование как опцию, но не требует его — решено отложить до реальной калибровки баланса на живых данных |
| `visited_sectors` — отдельная таблица | В самом перечне таблиц ТЗ такой сущности нет, но она необходима для отрисовки карты галактики — какие сектора уже видел именно этот игрок |
| WebSocket шлёт полный снапшот состояния, а не дельты изменений | Допустимая по ТЗ п. 11 задержка обновления интерфейса в 1–5 секунд делает протокол дельт преждевременной оптимизацией, которая не была нужна |
| Индикатор потока ОВМ/мин в шапке — клиентская оценка, не серверная величина | Сервер вообще не считает скорость потока как отдельную величину; оценка по разнице накопленного объёма между двумя снапшотами во времени оказалась вполне достаточной для того, чтобы индикатор выглядел живым |
| Буфер «вливается» в счётчик задачи только в момент её постановки | Ровно так, как описано в ТЗ п. 5; никакого дополнительного перетекания из буфера в уже стоящую в очереди задачу постфактум не предусмотрено |

## Известные ограничения MVP (кандидаты в бэклог)

- Строки журнала операций (`action_log.result`) локализованы только на
  русском языке — это отдельно доисследовано и частично устранено гораздо
  позже, в фазе 13, применительно к причинам недоступности приказов.
- Функция `game.applyState` после каждого нового снапшота состояния тихо
  перезапрашивает сразу обе карты (сектора и галактики) целиком — это можно
  было бы сузить, обновляя только ту карту, которую реально затронуло
  конкретное событие.
- Пагинация журнала операций реализована на сервере (курсор для запроса
  следующей страницы уже есть), но сам интерфейс на этом этапе показывает
  только самую первую страницу — 50 последних записей.
- У Rust-коннектора путь к папке с логами Claude Code пока жёстко зашит на
  значение по умолчанию (`~/.claude/projects`) — возможность настроить этот
  путь из интерфейса задумана как задел на экране Настроек (ТЗ п. 4.2.7), но
  ещё не реализована.
- Модель данных на этом этапе жёстко подразумевает «один игрок — один
  корабль»; колонка `players.params` типа jsonb намеренно зарезервирована
  под будущее расширение этой модели (которое в итоге и случилось в фазе 6).

## Как всё проверялось в MVP

`npm test` запускает 24 серверных теста на vitest против настоящего

## Часть II. Стратегическая фаза (фазы 6–13, ТЗ v0.02)

Вторая версия техзадания меняет сам жанр игры. Вместо одного корабля под
управлением игрока — целая флотилия разнородных сущностей (кораблей и
неподвижных построек вроде врат), которые делят между собой один общий
поток вычислительной мощности по приоритету. Вместо простой очереди задач —
полноценный раздел «Приказы» с явным разделением на доступные и недоступные
действия и понятными причинами отказа. Плюс три крупных новых блока
геймплея: стартовое ограничение одним сектором с выходом в остальную
галактику только через построенные врата и общую для всех игроков Цепь
Миров; База Знаний с деревом изучаемых технологий; и, наконец, опциональный
локальный ИИ-ассистент, с которым можно поговорить и которому можно отдать
команду на естественном языке.

Все архитектурные решения и отступления от буквы нового техзадания подробно
разложены по фазам в отдельном документе `docs/Strategy - Plan.md` — там
после каждой фазы есть блок «Итог» с историей того, что именно решили по
ходу реализации и почему. Здесь — тот же материал, но организованный иначе:
не «что решили», а «как это в итоге устроено и работает».

Важная деталь: мир существующих на момент миграции MVP-игроков был
безвозвратно вайпнут миграцией `0003_entities` — обратной совместимости со
старой однокорабельной моделью данных сознательно не делали, потому что сама
модель данных изменилась слишком фундаментально, чтобы аккуратно перенести
старые записи в новую форму имело смысл.

### Фаза 6 — сервер: флотилия и очереди по сущностям

Первая фаза второй волны разработки закладывает новую модель данных на
сервере — но делает это так, чтобы существующий клиент фазы 3–5 продолжал
играться, как будто ничего не изменилось, пока сам клиент не переписан.

**Модель сущности.** Таблица `ships`, где на игрока полагался ровно один
корабль, заменена на таблицу `entities`
([server/src/db/schema.ts](server/src/db/schema.ts)), в которой одной и той
же структурой описаны сразу два разных вида объектов игрока — и подвижные
корабли, и неподвижные постройки вроде будущих межзвёздных врат. Разница
между ними — не в отдельных таблицах, а в одном флаге `mobile` у класса
сущности, который читается из статичного каталога классов
[packages/shared/src/entities.ts](packages/shared/src/entities.ts). Таблица
`queues` тоже переехала на новую модель — получила колонку `entity_id`, и
первичным ключом строки очереди стала пара (`entity_id`, `slot`) вместо
прежней (`player_id`, `slot`). Таблица `cargo` точно так же теперь привязана
к конкретной сущности, а не к игроку в целом — потому что добыча ресурсов
физически привязана к координатам той сущности, которая её ведёт, и общий
«бездонный» трюм на всего игрока разом больше не имеет смысла. Сама миграция
`0003_entities.sql` не просто создаёт новую таблицу — она ещё и бэкфиллит
по одной записи в неё на каждого существующего на тот момент игрока,
перенося данные из старой таблицы `ships` (новая сущность получает класс
`scout_mk1` и имя «БОРТ-001»), а следующая миграция `0004_drop_ships`
удаляет уже ненужную старую таблицу целиком.

**Каскад ОВМ теперь распределяется по всей флотилии, а не по одному
кораблю.** Здесь принципиально важное архитектурное решение: единый общий
поток ОВМ на N параллельных очередей (по числу сущностей) распределяется
**строго по приоритету**, а не по круговому алгоритму (round-robin). Функция
`applyOvm` ([server/src/game/queue.ts](server/src/game/queue.ts)) теперь
сначала перебирает все сущности игрока в порядке приоритета, а тело
прежнего одноочередного цикла на одну-единственную очередь выделено в
отдельную функцию `pumpEntityQueue`, которая вызывается для каждой сущности
по очереди; если после исполнения задачи у сущности остался излишек ОВМ, он
каскадом уходит следующей по приоритету сущности, и так далее, пока поток не
иссякнет или не дойдёт до общего буфера. Важное свойство этого решения:
если приоритет всего одной сущности (то есть в точности старое MVP-
поведение), новый механизм даёт результат «бит-в-бит» идентичный старому —
поэтому весь набор тестов `queue.test.ts`, написанных ещё в фазе 2, был
перенесён без единой правки логики (только транспорт вызовов сменился на
`/orders/*` позже, в фазе 8). Отдельная тонкость: сущность, которая в данный
момент находится в кулдауне перед исполнением, теперь **пропускается** в
каскаде, а не обрывает его целиком — иначе одна-единственная сущность в
кулдауне замораживала бы поток ОВМ для всей остальной флотилии, что явно
противоречило бы самой идее управления несколькими кораблями сразу.

**Домашний сектор.** Новая функция `pickHomeSector`, использующая тот же
детерминированный генератор случайных чисел, что и генерация мира
(`createRng(playerId + galaxySeed)`), выдаёт каждому игроку псевдослучайный
домашний сектор в увеличенной галактике размером 32×32 (раньше было 10×10)
— см. [server/src/routes/auth.ts](server/src/routes/auth.ts). Этот домашний
сектор сохраняется в новой колонке `players.home_sector_id` и станет якорем
для механики Цепи Миров в фазе 11.

**Новое API.** Маршруты постановки, удаления и перестановки приказов
(`POST /orders/add|remove|reorder`) теперь принимают конкретный `entityId` —
какой именно сущности флотилии адресован приказ. Плюс два совсем новых
маршрута: `POST /fleet/priority` (задать порядок распределения ОВМ между
сущностями) и `POST /fleet/rename` (переименовать сущность).

**Тесты фазы** (`server/test/fleet.test.ts`) проверяют: каскад ОВМ корректно
распределяется между двумя сущностями, кулдаун одной сущности не
останавливает поток для другой, приоритет реально соблюдается на практике,
и, отдельно, что при единственной сущности на игрока поведение полностью
совпадает со старым MVP.

### Фаза 7 — клиент: новый каркас интерфейса и раздел «Флотилия»

Седьмая фаза заново перестраивает клиентскую архитектуру, прежде чем
добавлять любой новый функционал сверху — иначе каждый новый экран пришлось
бы вписывать в уже нездоровую структуру трижды.

**Снятие тройного хардкода экранов.** До этой фазы список из семи экранов
терминала был буквально продублирован в трёх независимых местах кода
одновременно: в TypeScript-типе `Screen` (union из семи строковых
литералов), в отдельном массиве `MENU` для отрисовки меню, и в длинной
цепочке условных блоков `{#if}` внутри `App.svelte`, которая решала, какой
именно компонент экрана показать. Добавление всего одного нового экрана
требовало правки во всех трёх местах согласованно — забыть одно из них было
легко, а последствия — незаметны, пока не попробуешь именно этот новый
экран открыть. Решение — единственный источник истины,
[client/src/lib/screens.ts](client/src/lib/screens.ts): простой массив
объектов вида `{id, key, label, component}`, из которого автоматически
выводятся и содержимое меню, и назначение горячих клавиш (сначала цифры от
`1` до `9`, а после — `0`), и сам React/Svelte-компонент экрана; `App.svelte`
теперь просто рендерит весь массив `SCREENS` целиком одним циклом.
Добавление нового экрана с этого момента — ровно одна новая строка в одном
файле, и именно так это дальше и происходило — в фазе 10 (База Знаний) и в
фазе 12 (Ассистент).

**Исправление блокировки клавиатуры текстовым вводом.** Здесь обнаружился
неприятный баг, унаследованный ещё с MVP: глобальный обработчик нажатий
клавиш в `App.svelte` был зарегистрирован в DOM раньше, чем обработчики
отдельных экранов, а значит вызов `stopPropagation()` внутри экрана его
попросту не мог остановить — событие уже успевало долететь до глобального
обработчика первым. Практическое следствие: если бы на каком-то экране
появилось текстовое поле ввода (как в итоге и появилось — сначала поиск по
Базе Знаний, потом чат ассистента), нажатие цифровой клавиши прямо во время
набора текста переключало бы весь экран приложения, а не печатало цифру.
Решение — новый геттер `game.keysCaptured`
([client/src/lib/game.svelte.ts](client/src/lib/game.svelte.ts)), который
проверяет `document.activeElement instanceof HTMLInputElement /
HTMLTextAreaElement` **прямо в момент проверки**, а не читает заранее
сохранённый булев флаг. Это намеренное решение, а не просто стиль: в первой
пробной версии такой флаг (`inputFocused`) действительно использовался, и
он однажды «залип» в значении true при определённой последовательности
действий, намертво заблокировав всю клавиатуру приложения до перезагрузки
страницы — а проверка состояния DOM по факту в принципе не может так
рассинхронизироваться с реальностью, потому что она эту реальность и
спрашивает напрямую. С этого момента все глобальные обработчики клавиш в
приложении — и в `App.svelte`, и в компоненте `Tree.svelte`, и в отдельных
экранах с собственными горячими клавишами — единообразно проверяют
`!game.keysCaptured` перед тем, как что-либо делать.

**Общие переиспользуемые компоненты.** В новой папке
`client/src/lib/terminal/` появились: `Overlay.svelte` — базовая модалка,
которая сама считает вложенность (`game.modalDepth`), чтобы несколько
модалок могли корректно накладываться друг на друга; `Confirm.svelte` —
готовый диалог подтверждения действия (`Enter`/`Y` — да, `Esc`/`N` — нет);
`ListPicker.svelte` — выбор одного варианта из списка, с поддержкой
затенённых недоступных пунктов и пояснительной подписи к каждому.
Компонент `Tree.svelte` (плоская клавиатурная навигация по дереву с
раскрывающимися узлами) на этом этапе ещё не появился — решено было не
строить его вслепую, а дождаться фазы 8, где раздел «Приказы» станет его
первым настоящим потребителем и подскажет, какой именно API компоненту
реально нужен.

**Экран «Флотилия»**
([client/src/screens/Fleet.svelte](client/src/screens/Fleet.svelte)) — новый
раздел интерфейса со списком всех сущностей игрока (название, класс,
текущий статус, координаты), панелью подробной информации, которая
наполняется либо по наведению мыши на строку списка, либо по клавиатурному
курсору (с плавным откатом на последнее выбранное значение, если курсор
никуда конкретно не наведён), возможностью сразу отдать приказ прямо из
списка, изменить приоритет распределения ОВМ клавишами `[+]`/`[-]` и
переименовать сущность клавишей `[R]`.

### Фаза 8 — раздел «Приказы»

Восьмая фаза превращает простую очередь одного корабля в полноценный
инструмент управления целой флотилией (ТЗ v0.02 п. 3) — с явным списком
того, что каждой сущности доступно прямо сейчас, а что нет и почему.

Новый серверный модуль
[server/src/game/orders.ts](server/src/game/orders.ts) построен как
дополнительный слой **поверх** уже существующей функции `validateAction`, а
не как параллельная, отдельно поддерживаемая копия тех же правил — это
принципиальный выбор, потому что две независимые копии одной и той же
логики валидации рано или поздно неизбежно разъезжаются между собой.
Реализовано это через третий режим валидации, `'offer'` (в дополнение к уже
существовавшим `enqueue` и `activate`) — он проверяет общие условия
действия без привязки к какой-то конкретной цели, и именно он гарантирует,
что список «это доступно» на экране никогда не разойдётся с тем, что
реально примет `POST /orders/add`, когда игрок попробует это действие
поставить в очередь. Есть здесь и отдельный важный инвариант: функция
`listOrders` дополнительно сама проверяет, не заполнена ли уже вся очередь
сущности (по числу занятых слотов, `orderSlots`) — потому что сама
`validateAction` этого не делает, и без отдельной проверки список
доступности мог бы показать действие доступным, хотя реальная постановка в
очередь тут же отклонилась бы из-за нехватки свободного слота.

Новый эндпоинт `GET /orders/available[?entityId=]` отдаёт на каждую сущность
(или на все сразу, если параметр не указан) целый массив вариантов —
`OrderOption {action, costOvm, available, reason, target, candidates?}`. Для
действий, у которых целью служит конкретный объект (`target === 'object'`),
дополнительно приходит список реальных кандидатов рядом — то есть тех
объектов, которые игрок уже знает благодаря сканированию и которые
физически находятся в радиусе действия.

На клиенте новый экран
[client/src/screens/Orders.svelte](client/src/screens/Orders.svelte)
построен как раз на только что появившемся компоненте `Tree.svelte`:
верхний уровень дерева — сущности флотилии, у каждой есть собственный
статус-бар готовности, ниже — занятые слоты очереди, ещё ниже — раскрытый
список «ДОСТУПНЫЕ ПРИКАЗЫ», и наконец свёрнутый по умолчанию, затенённый
узел «НЕДОСТУПНЫЕ (k)» с явной причиной у каждого недоступного варианта —
игрок сразу видит не только что можно, но и почему нельзя. Групповой приказ
реализован как простая веерная рассылка: один запрос `POST /orders/add`
с массивом `entityIds`, где каждая сущность из массива валидируется
полностью независимо от остальных, и часть группы вполне может отклониться,
не блокируя постановку приказа остальным (в ответе приходит массив
`results: {entityId, ok, reason?}[]` — по одному результату на сущность).
Старый экран `Queue.svelte` вместе с его серверными алиасами
(`routes/queue.ts`) на этом этапе удалён целиком, а устаревшие поля из
`StateResponse` (`ship`/`queue`/`cargo`), которые сохранялись только для
обратной совместимости со старым клиентом с фазы 6, тоже убраны — экраны
«Трюм» и «Статус» переведены на работу через сущности напрямую.

Тесты фазы (`orders.test.ts`) проверяют вычисление доступности сама по
себе: недоступные цели, пока ничего не отсканировано, появление кандидата
сразу после подлёта к нему, полный отказ всей очереди при заполнении всех
слотов, что неподвижный класс сущности (например, будущие врата) вообще не
предлагает действие «переместиться», фильтрацию по конкретному `entityId` и
запрос по всей флотилии без фильтра сразу. Старый набор тестов движка
(`queue.test.ts` — каскад, «НЕВЫПОЛНИМО», кулдаун, идемпотентность, лимиты)
перенесён на новый транспорт запросов без единого изменения проверяемых
инвариантов самого движка — только маршруты, через которые тест обращается
к серверу, стали другими.

### Фаза 9 — классы, модули, взаимодействие и минимальная боёвка

Девятая фаза наполняет содержимым три приказа, которые до этого были
заглушками — `interact`, `attack` и `special` — и вводит классы сущностей
с модулями, которые определяют, что именно конкретный корабль умеет делать
(ТЗ v0.02 п. 3.2).

Каталог `MODULES`
([packages/shared/src/entities.ts](packages/shared/src/entities.ts))
получил содержимое: `mining_laser`, `railgun`, `refinery`, `survey_array` —
у каждого модуля есть поле `grants: ActionType[]` (какие действия он
разрешает) и, отдельно у оружия, поле `damage`. Функция
`hasModuleGranting(entity, action)`
([server/src/game/entities.ts](server/src/game/entities.ts)) стала гейтом,
который проверяется в `game/orders.ts` **раньше**, чем поиск кандидатов
цели — это важный порядок, потому что если бы проверка модуля шла после
поиска целей, безмодульная сущность, случайно оказавшаяся рядом с реальной
целью, увидела бы обманчивую причину отказа «НЕТ РЕСУРСА РЯДОМ» вместо
честной «НЕТ МОДУЛЯ» — то есть выглядело бы так, будто дело в отсутствии
подходящей цели, хотя на самом деле дело в отсутствии оборудования.

| Приказ | Условие выполнимости | Что происходит |
|---|---|---|
| `interact` | станция или врата в радиусе действия (`nearDistance`) | Приказ сам решает, стыковаться или расстыковываться, глядя на текущее значение `dockedObjectId` сущности — отдельный вызов `/ship/undock` из MVP полностью удалён, это больше не самостоятельная операция, а просто одна из двух сторон одного и того же приказа |
| `attack` | у сущности есть модуль с уроном, она находится ровно в тех же координатах, что и цель, а у цели выставлено свойство `attackable` | Урон вычитается из запаса прочности цели (`props.hp`); когда он доходит до нуля, цель уничтожается и оставляет после себя контейнер с точным набором лута (эта часть переиспользует уже существующий приказ `pickup`, а не изобретает отдельный механизм) |
| `special` | модуль с `grants: ['special']` | Приказ реализован полностью и работает технически, но по-честному недоступен вообще всем существующим классам сущностей — ни один модуль пока не даёт `grants: ['special']`. Это осознанный резерв под будущий контент из ТЗ, а не заглушка в смысле «код не дописан» |

Поля `hp`/`hp_max` заводятся сразу у всех сущностей игры (отдельная миграция
`0004_entity_hp`), хотя PvP-боёвка между игроками и ответный огонь со
стороны противника явно отложены на будущее — реализованная боёвка строго
одиночная и детерминированная: один игрок наносит урон одной цели, без
какой-либо реакции с её стороны и без таймеров (это прямая, осознанная
развязка одного из открытых вопросов исходного ТЗ, подробнее — в
`Strategy - Plan.md`, часть III).

При живой проверке этой фазы обнаружился и был исправлен настоящий баг
слияния конфига: в базе данных к тому моменту лежала устаревшая строка
`game_config.actionCosts`, сохранённая ещё до переименования действий
(`jump_local` в `move` и так далее), и при мягком слиянии вида
`{...defaults, ...stored}` эта устаревшая строка **целиком** перекрывала
собой свежие дефолты — из-за чего новые ключи вроде `move`, `attack` и
`special` читались как `undefined`. Живьём это проявлялось буквально как
надпись «ПРЫЖОК В СЕКТОРЕ (undefined ОВМ)» в интерфейсе. Исправление —
точечный «глубокий» merge именно для вложенных объектов конфига
(`actionCosts`/`conversion`/`limits`) в функции `mergeGameConfig`
([server/src/game/config.ts](server/src/game/config.ts)); при этом
верхнеуровневые плоские поля конфига по-прежнему сливаются мелко и
намеренно — это решение отдельно объясняется и подтверждается уже в
фазе 13.

### Фаза 10 — База Знаний и Технологии

Десятая фаза добавляет игроку возможность накапливать знания о мире и
превращать их в новые технологические возможности (ТЗ v0.02 пп. 5–6).

Содержимое самой Базы Знаний и дерева технологий — это статичный каталог в
коде,
[packages/shared/src/knowledge.ts](packages/shared/src/knowledge.ts)
(`KNOWLEDGE_ENTRIES` и `TECHS`, разбитые на три ветки — навигация,
промышленность, оборона), а в базе данных хранится только личный прогресс
каждого игрока по этому каталогу — какие записи он уже открыл и какие
технологии уже изучил (таблицы `player_knowledge` и `player_tech`,
миграция `0005_knowledge.sql`). Связующим звеном между технологиями и
остальной игровой логикой служит единый тип `Capability` — например,
`{kind: 'order', order: 'attack'}` — который описывает, что именно
открывает изученная технология; читают этот тип и `game/orders.ts` (чтобы
понять, доступно ли действие), и `game/actions.ts` (чтобы проверить условие
при непосредственном исполнении). На момент этой фазы реально гейтит
движок только одна технология — `def.weapons`, которая открывает приказ
`attack` — остальные существуют как полностью рабочий, но пока не
подключённый к проверкам резерв: весь цикл их изучения работает от начала
до конца, просто соответствующий `Capability` ещё нигде не проверяется,
точно так же, как приказ `special` в предыдущей фазе.

**Загрузка данных.** Новый приказ `upload_data` не принимает параметров
вообще — сервер сам находит в трюме сущности контейнер, у которого в
свойствах стоит `props.contents === 'data-core'` (генератор мира такие
контейнеры уже умел создавать и раньше, к этой фазе в них лишь добавили
детерминированный `props.entryId` — какую именно запись Базы Знаний
конкретный контейнер открывает), и открывает соответствующую запись через
функцию `unlockEntry`
([server/src/game/knowledge.ts](server/src/game/knowledge.ts)). Благодаря
этому решению общий тип `ActionParams` вообще не пришлось трогать — приказу
не нужен `objectId`, потому что контейнер и так уже находится в трюме той
самой сущности, которая исполняет приказ.

**Исследование технологии** — это не приказ флоту вообще, а мгновенное
действие интерфейса управления: `POST /tech/research`
([server/src/routes/knowledge.ts](server/src/routes/knowledge.ts))
списывает стоимость исследования прямо из общего буфера ОВМ внутри одной
транзакции с блокировкой строки игрока (`lockPlayer`), минуя очередь
приказов целиком — точно так же, как позже, в фазе 12, будет списываться
плата за обращение к ассистенту. Разница с приказами принципиальна: это
не то, что делает флот, а то, что игрок делает сам, немедленно, как
покупку в интерфейсе управления.

На клиенте новый экран
[client/src/screens/Knowledge.svelte](client/src/screens/Knowledge.svelte),
тоже построенный на компоненте `Tree.svelte`, показывает два раздела:
«Записи» с возможностью искать по подстроке (ТЗ v0.02 п. 5), и
«Технологии» — уже изученные (отмечены галочкой, с описанием ветки при
наведении) вместе с теми, что доступны к изучению прямо сейчас, а если
какой-то технологии чего-то не хватает — конкретная причина (недостающие
записи, недостающие требования по дереву, недостаточно средств в буфере).

### Фаза 11 — стартовые ограничения, врата и Цепь Миров

Одиннадцатая фаза реализует, пожалуй, самое ощутимое для игрока новое
правило из ТЗ v0.02 п. 4: новый игрок оказывается заперт в своём
собственном псевдослучайном домашнем секторе (том самом, который был выдан
ещё в фазе 6), пока не изучит технологию гиперпрыжка и не построит
собственные врата.

**Модель графа Цепи Миров** —
[server/src/game/chain.ts](server/src/game/chain.ts). Таблица `sector_links`
хранит рёбра этого графа как **неориентированные и общие сразу для всех
игроков** — то есть сама топология Цепи никому не скрыта, в отличие от
содержимого отдельных секторов, которое по-прежнему открывается только
сканированием и анализом. Каждое ребро хранится в канонической форме, где
первый идентификатор сектора лексикографически меньше второго — иначе пары
`(a, b)` и `(b, a)` считались бы двумя разными рёбрами графа, что было бы
явной ошибкой модели данных. Отдельная таблица `chain_keys` — это уже
заготовленная точка будущей монетизации (ТЗ п. 4): у ключа может быть либо
конкретный целевой сектор, либо `null`, что означает «в случайный уже
подключённый к Цепи мир» — конкретный сектор для такого ключа выбирается
только в момент применения, а не заранее в момент выдачи.

**Постройка врат.** Новый приказ `build_gate` стоит целых 250 000 ОВМ, и это
число **намеренно больше**, чем кап общего буфера (100 000) — то есть
построить врата, просто накопив ОВМ в общем буфере, физически невозможно:
единственный способ — постепенно накапливать эту сумму прямо в счётчике
прогресса самого приказа на протяжении многих игровых сессий. Каскадный
механизм начисления к этому моменту уже прекрасно умел работать именно так
— переделывать в движке не пришлось вообще ничего, потребовалось только
задать такую высокую стоимость. Постройка самых первых врат в игровом мире
не подключает их ни к чему — функция `joinChainOnGateBuilt` в этом случае
просто возвращает `null`, и врата становятся «первым узлом Цепи». А вот
вторые и все последующие врата, построенные где угодно во всём мире,
подключаются автоматически к случайно выбранному уже существующему узлу —
именно через самый обычный `Math.random()`, а не через тот же
детерминированный `createRng`, что используется для генерации мира: это
осознанное различие, потому что подключение к Цепи — разовое игровое
событие, которое не обязано (и не должно) быть детерминированно
воспроизводимым, в отличие от содержимого секторов.

**Приказ гиперпрыжка теперь требует сразу трёх условий одновременно**
([server/src/game/actions.ts](server/src/game/actions.ts)): изученную
технологию `nav.hyperjump`, собственные врата игрока именно в ТЕКУЩЕМ
секторе (эта часть проверяется сразу при постановке приказа в очередь, а не
только при активации — иначе игрок узнавал бы о принципиальной
невозможности прыжка только постфактум, через статус «НЕВЫПОЛНИМО» в
журнале, что выглядело бы куда менее понятно), и, наконец, реальное ребро в
графе `sector_links` до сектора назначения (а вот это условие проверяется
уже на активации приказа, точно так же, как раньше проверялись координаты
цели). Старая проверка простого соседства секторов
(`sectorsAdjacent`), которая раньше вообще была единственным условием
гиперпрыжка, из правил перемещения удалена полностью — теперь единственный
способ попасть в другой сектор дальним прыжком — это связность через Цепь
Миров.

**Применение ключа Цепи** (`POST /chain/connect`) привязано именно к
**домашнему сектору игрока**, а не к текущему положению его ведущей
сущности — это осознанный выбор, который делает поведение однозначным даже
если игрок впоследствии построит вторые врата ещё где-то ещё; для
применения ключа обязательно требуются собственные врата игрока именно в
домашнем секторе.

На клиенте экран
[client/src/screens/GalaxyMap.svelte](client/src/screens/GalaxyMap.svelte)
теперь рисует поверх обычной сетки посещённых секторов ещё и связанные
Цепью сектора отдельным символом (`◆`), а также показывает, какие из связанных
секторов реально достижимы прямо сейчас (поле `galaxy.reachable`, которое
сервер вычисляет обходом в ширину по всему графу `sector_links` —
[server/src/routes/map.ts](server/src/routes/map.ts)). Здесь же появилась
панель ключей Цепи Миров с кнопкой «Применить» на каждый ещё не
использованный ключ и отдельной дебаг-кнопкой для выдачи тестового ключа.

### Фаза 12 — ИИ-ассистент (опционально, ТЗ v0.02 п. 7)

Двенадцатая фаза добавляет то, что в самом техзадании прямо помечено как
опциональное — чат с локальной ИИ-моделью, которой можно задать вопрос в
рамках уже открытых игроком знаний или дать команду флоту на естественном
языке. Критерий приёмки этой фазы прямо требует, чтобы при отсутствии
локально запущенной модели экран честно сообщал об этом, а не ронял всю
остальную игру — то есть отсутствие ассистента не должно быть заметно
нигде, кроме самого его экрана.

**Разделение авторитетности между сервером и клиентом.** Сервер остаётся
единственным источником того, что именно ассистенту разрешено «знать», и
единственным, кто списывает за это плату:
`POST /assistant/prepare`
([server/src/routes/assistant.ts](server/src/routes/assistant.ts))
списывает фиксированную стоимость (`assistantCostOvm`, по умолчанию 300)
из общего буфера **при каждом отдельном обращении** — это не одноразовая
покупка навсегда, как исследование технологии, а плата за каждый
конкретный вопрос или команду — и в ответ отдаёт только те записи Базы
Знаний, которые игрок уже реально открыл, той же самой функцией
`unlockedEntryIds`, которую использует и обычный `GET /knowledge`. При
этом сам разговор с моделью — то, что она отвечает, какие слова
использует — сервер вообще никогда не видит: это целиком происходит на
клиенте.

**Как клиент добирается до Ollama сквозь ограничения Tauri.** В собранном
Tauri-приложении веб-часть интерфейса живёт на отдельном внутреннем origin,
и прямой браузерный `fetch()` к локальному адресу Ollama упёрся бы в CORS,
если специально не настраивать переменную окружения `OLLAMA_ORIGINS`
вручную на машине игрока — то есть обычному игроку пришлось бы лезть в
настройки стороннего приложения, что явно не годится. Решение — плагин
`@tauri-apps/plugin-http`
([client/src-tauri/src/lib.rs](client/src-tauri/src/lib.rs):
`.plugin(tauri_plugin_http::init())`, с правом доступа `http:default`,
ограниченным адресами `localhost`/`127.0.0.1` в
`capabilities/default.json`) — запрос в этом случае реально уходит из
Rust-части приложения, где никакого браузерного CORS попросту не
существует. В обычной браузерной сборке (без Tauri-окна) используется
самый обычный `fetch` — тот же путь, что и у всех остальных запросов
приложения. Вся эта развилка транспорта сосредоточена в одной функции
`httpFetch` в
[client/src/lib/assistant.svelte.ts](client/src/lib/assistant.svelte.ts).

**Замкнутая, проверяемая схема действий.** Вместо отдельной JSON-схемы или
библиотеки вроде `zod` (которая в проекте вообще нигде не используется —
везде ручные проверки плюс типизированные через discriminated union
структуры TypeScript, и здесь решено следовать тому же стилю) реализованы
два простых инструмента в формате OpenAI function-calling: `issue_order` и
`research_tech`. Функция `resolveToolCall` сверяет то, что вернула модель,
с тем же самым `GET /orders/available`/`GET /tech`/`galaxy.reachable`,
которые видит и обычный интерфейс игрока — то есть модель **физически не
может** предложить несуществующую сущность, недоступный приказ или цель,
которой не существует: любая такая попытка просто отклоняется резолвером
до того, как дойти до реального запроса на сервер. Свободный текст модели,
не оформленный как явный вызов одного из этих двух инструментов, никогда
не приводит ни к какому действию — он просто показывается как обычная
реплика в чате. А исполнение уже подтверждённого игроком вызова идёт через
уже существующие, ничем не привилегированные функции —
`game.enqueue`/`api.techResearch` — то есть ассистент в буквальном смысле
не может сделать ничего, чего не мог бы сделать сам игрок вручную теми же
самыми кнопками.

**Решение отказаться от стриминга ответа** в первой версии — сознательное
отклонение от изначального черновика плана. У OpenAI-совместимого API
потоковая передача означает, что вызов инструмента (`tool_calls`)
приходит по частям, и кусочки его аргументов нужно аккуратно склеивать
между чанками — а именно вызов инструмента, то есть постановка реального
приказа, описан в техзадании как самое ядро фичи, а не просто побочная
возможность «заодно». Обычный, не потоковый ответ проще и надёжнее
разобрать целиком; добавить стриминг для чисто текстовых ответов без
вызова инструментов можно будет и позже отдельным патчем, без изменения
самого контракта.

**Живая калибровка с настоящей моделью** (`qwen2.5:3b` через Ollama)
вскрыла и позволила исправить три отдельных бага до сдачи фазы: во-первых,
`POST /assistant/prepare`, вызванный вообще без тела запроса, ловил 400-ю
ошибку от Fastify (тело JSON-запроса с заголовком `Content-Type` не может
быть пустым) — исправлено отправкой пустого объекта `'{}'`. Во-вторых,
пример-заготовка внутри самого описания tool-схемы, показанный модели как
образец правильного вызова, заставлял небольшую локальную модель просто
скопировать этот пример буквально, вместо того чтобы прочитать реальную
сводку флота и подставить настоящие данные — переписано так, чтобы в
описании не было ни одного конкретного значения, которое можно было бы
скопировать вместо настоящего. В-третьих, мелкая локальная модель иногда
самовольно транслитерирует кириллические имена сущностей латиницей (то есть
«БОРТ-002» превращается в «BORT-002») — добавлено резервное сопоставление
по фонетическому «скелету» имени внутри функции `findEntityByName`, чтобы
такая транслитерация не мешала резолверу узнать нужную сущность.

#### Дополнение к Фазе 12 — встроенный движок Ollama (готовим дистрибуцию через Steam)

Уже после того, как основная часть фазы 12 была сдана, всплыл важный
практический вопрос: живой, отдельно запущенный Ollama на машине игрока —
это обязательное условие для работы ассистента, но при распространении игры
через Steam такую внешнюю зависимость ставить попросту неоткуда — нельзя
рассчитывать, что случайный покупатель игры в Steam уже имеет на своей
машине заранее настроенную локальную LLM. Решение: **сам движок Ollama
зашивается прямо в установку игры**, а модель для него (около 2 гигабайт)
скачивается отдельно, только по явному согласию игрока, в момент первого
реального обращения к ассистенту — так базовый размер самой игры не растёт
для тех игроков, которые ассистентом вообще не пользуются.

Ключевая находка, которая и сделала это решение практичным: полный
официальный дистрибутив Ollama тяжёлый не из-за самого движка как такового,
а почти целиком из-за бэкендов аппаратного ускорения на видеокартах — CUDA
двух версий, ROCm, Vulkan — которые Ollama поставляет все разом и выбирает
нужный уже во время работы, в зависимости от того, какое железо у
пользователя. На диске это всё вместе — 2.85 гигабайта. Без этих бэкендов —
то есть сам исполняемый файл `ollama.exe` (34.6 мегабайта) плюс
CPU-библиотеки семейства `ggml-cpu-*.dll`/`libllama*.dll` (ещё около 35
мегабайт) — реально нужный движок компактен. Новый скрипт
`client/scripts/fetch-ollama-sidecar.mjs` скачивает официальный
Windows-архив `ollama-windows-amd64.zip` (1.5 гигабайта — он уже без ROCm
и MLX, они распространяются отдельными архивами), вырезает из него папки
CUDA и Vulkan и складывает итоговый результат — 70.7 мегабайта — в папку
`client/src-tauri/binaries/` под именем, которое ожидает механизм Tauri под
названием «sidecar» (внешний исполняемый файл, который упаковывается прямо
вместе с приложением и запускается напрямую, без какой-либо системной
установки — тот же самый принцип, каким в проекте уже давно жил
`bin/connector_cli.rs`, только на этот раз исполняемый файл сторонний, а не
свой собственный). Сам этот бинарник не хранится в git-репозитории — он
слишком большой для этого — а готовится заново каждый раз перед сборкой
(`tauri dev` или `tauri build`) этим скриптом; конфигурация
`tauri.conf.json` регистрирует и сам файл, и соседнюю папку с библиотеками
для итоговой упаковки.

**Игра не трогает уже работающий у игрока Ollama.** Вся эта логика целиком
на клиенте, в
[client/src-tauri/src/ollama.rs](client/src-tauri/src/ollama.rs): команда
`ollama_ensure_running` сначала всегда проверяет, не отвечает ли уже
что-нибудь по настроенному адресу — и если да (это может быть собственный
Ollama игрока, например, с полноценным аппаратным ускорением на его
видеокарте), команда вообще ничего не предпринимает, оставляя всё как
есть. И только если по этому адресу никто не отвечает, она поднимает
встроенный sidecar через плагин `tauri-plugin-shell`, дополнительно указывая
ему хранить модели в изолированной папке внутри стандартной папки данных
приложения — чтобы никак не путаться с возможной чужой установкой Ollama и
её собственными моделями.

**Найденный при живой проверке баг.** Ollama в ответ на запрос списка
моделей отдаёт `"data": null`, если моделей ещё не загружено ни одной — а
не пустой массив `"data": []`, как можно было бы интуитивно ожидать. Без
специальной обработки этого случая используемая на стороне Rust библиотека
сериализации `serde` просто не может разобрать `null` в поле типа `Vec<T>`,
и разбор ответа целиком проваливался с ошибкой — из-за чего команда решала,
что сервер вообще ничего не ответил, и на каждой попытке проверки заново
пыталась поднять ещё одну копию sidecar-процесса поверх уже прекрасно
работающего. Исправление — обернуть поле в `Option`
(`#[serde(default)] data: Option<Vec<ModelEntry>>`) и подставлять пустой
список через `.unwrap_or_default()`, если пришёл `null`. Особенность этого
бага в том, что он проявляется не в каком-то редком краевом случае, а ровно
в том состоянии, в котором свежеподнятый sidecar находится сразу после
самого первого своего запуска — поэтому он был пойман буквально на первой
же живой проверке, а не спрятался где-то глубже.

**Скачивание модели — только по явному действию игрока.** Функция
`pullModel`
([client/src/lib/assistant.svelte.ts](client/src/lib/assistant.svelte.ts))
потоково читает ответ на `POST /api/pull` — это «родной» эндпоинт самого
Ollama, отдельный от уже использовавшегося OpenAI-совместимого пути `/v1`,
поэтому адрес сервера для этого конкретного запроса специально очищается от
суффикса `/v1` — через тот же самый `httpFetch`, разбирая приходящий
построчно JSON с полями `status`/`completed`/`total` через низкоуровневый
`response.body.getReader()`. Диалог с явным подтверждением и указанием
примерного объёма загрузки (~2 гигабайта) показывается либо в самом чате
ассистента при первом обращении, если нужной модели ещё нет, либо
отдельной кнопкой «Скачать модель» на экране Настроек — и ни при каких
других обстоятельствах сама по себе загрузка не запускается.

Живая проверка (через `npm run tauri dev`) показала: собственный
`ollama.exe`, запущенный из собранного каталога приложения (а не из
отдельно установленной на машине копии), поднимался автоматически сразу
при входе игрока в игру, и при повторных проверках не порождал вторую
параллельную копию процесса; формат ответа `/api/pull` отдельно подтверждён
прямым запросом к уже поднятому sidecar-процессу и совпал с тем, что
разбирает клиентский код. Что осталось непроверенным честно: полная
упаковка `tauri build` (то есть работает ли механизм `bundle.resources` уже
в собранном инсталляторе, а не только в режиме разработки) и полное
скачивание модели до конца — сам формат потока подтверждён без того, чтобы
дожидаться реальных двух гигабайт целиком. Область реализации пока — только
Windows; sidecar-бинарники для macOS и Linux ещё не подготовлены.

### Фаза 13 — надёжность, баланс, полировка

Тринадцатая, последняя на данный момент фаза — не про новый геймплей, а про
то, чтобы уже реализованное держалось надёжно под нагрузкой и не теряло
данные при сбоях, плюс здесь же написана вся эта документация.

**Живая калибровка баланса без пересборки клиента** оказалась уже
полностью готовым механизмом, унаследованным ещё из MVP — отдельный
таймер в [server/src/index.ts](server/src/index.ts) перечитывает таблицу
`game_config` раз в 60 секунд, и новые плоские поля вроде появившейся в
фазе 12 стоимости обращения к ассистенту (`assistantCostOvm`) подхватываются
этим механизмом автоматически, без единой правки кода — просто в силу того,
как устроено мягкое слияние `{...defaults, ...stored}`. Отдельного внимания
по-прежнему требуют только вложенные объекты конфига вроде `actionCosts`
(см. фазу 9) — и это уже отдельно покрыто тестом `config.test.ts`.

**Сброс игрового мира без потери истории начислений.** Новый скрипт
`server/scripts/wipe.ts` должен уметь стереть весь игровой мир (флотилии,
сектора, объекты, накопленные знания, Цепь Миров), но при этом **ни в коем
случае** не трогать таблицу `credit_ledger` — потому что монотонность
идентификаторов пакетов там критически важна для дедупликации на стороне
Rust-коннектора — и не трогать `game_config`, потому что это операционная
калибровка баланса, а не состояние игрового мира. При разработке этого,
казалось бы, простого скрипта нашлась нетривиальная особенность самого
PostgreSQL: команда `TRUNCATE players CASCADE` каскадирует в связанные по
внешнему ключу таблицы **независимо** от того, какое поведение при удалении
(`ON DELETE`) было явно указано при объявлении этого внешнего ключа — это
специфика именно команды `TRUNCATE ... CASCADE`, а не обычного `DELETE`,
где такое поведение как раз учитывалось бы. Первая версия скрипта из-за
этого молча стирала бы леджер начислений вместе с игроками, прямо
противореча собственному требованию не трогать его. Решение оказалось
простым, хоть и не сразу очевидным: строки таблицы `players` вообще не
удаляются целиком — вместо этого сбрасываются только их изменяемые игровые
поля (`ovm_buffer`, `home_sector_id`) через обычный `UPDATE` — это
единственный способ сохранить леджер начислений нетронутым, пока между ним
и таблицей игроков сохраняется живая связь по внешнему ключу.

**Нагрузочная проверка каскада ОВМ.** Новый тест `server/test/load.test.ts`
создаёт одному игроку сразу 10 сущностей флотилии, у каждой — задача,
готовая к завершению, и проверяет, что один-единственный тик серверного
свипа (`sweepQueueCompletions`) действительно доводит до конца все десять
задач сразу и укладывается в разумный бюджет времени. Смысл этого теста не
в измерении абсолютной скорости конкретного железа, а в страховке от
будущей регрессии в сложности алгоритма: функция `applyOvm` и так делает
до `fleet.length + 2` проходов по всей флотилии на каждый вызов, и если
однажды кто-то случайно сделает эту сложность квадратичной, тест должен
это заметить.

**Проверка переживания рестартов для новых таблиц.** То, что в MVP (в фазе
5) проверялось только архитектурным рассуждением плюс ручным
kill-и-перезапуском Rust-коннектора, для новых таблиц, появившихся в фазах
6–12, теперь проверяется полностью автоматически новым тестом
`server/test/restart.test.ts`: приказ намеренно останавливается на
промежуточном значении прогресса, первый процесс серверного приложения
закрывается совсем, и поверх **той же самой** базы данных, без пересоздания
с нуля, поднимается второй, независимый процесс — после чего состояние
(включая данные из таблиц `player_knowledge`, `player_tech`, `sector_links`,
`chain_keys`, которых в MVP-версии этого теста попросту не существовало)
сверяется побитово, а отдельно проверяется, что повторная отправка того же
самого пакета начисления ОВМ уже после «рестарта» по-прежнему корректно
распознаётся как повтор — то есть идемпотентность леджера переживает смену
процесса, а не только смену сетевого соединения.

**Аудит переводов на английский язык.** Отдельная сверка каждого
литерального русского текста внутри вызовов функции перевода `t(...)` по
всему клиентскому коду — причём не только по логам того, что реально
показывалось на экране во время предыдущих ручных проверок, а по факту,
статическим поиском по исходникам, вместе со значениями словарей
`ACTION_LABELS`/`STATUS_LABELS`/`BRANCH_LABELS` и всеми реальными строками
причин отказа из `game/actions.ts` и `game/orders.ts` — нашла и закрыла два
отдельных класса пропусков в
[client/src/lib/i18n.svelte.ts](client/src/lib/i18n.svelte.ts). Во-первых,
короткая форма пункта меню «БАЗА ЗНАНИЙ»: в словаре был перевод только для
полного заголовка панели «БАЗА ЗНАНИЙ И ТЕХНОЛОГИИ», а короткая версия,
которая используется именно в пункте меню, оставалась непереведённой.
Во-вторых, целых 19 причин недоступности приказов, добавленных ещё в фазах
6–9 (вроде «ОЧЕРЕДЬ ЗАПОЛНЕНА», «СУЩНОСТЬ НЕПОДВИЖНА», «ЦЕЛЬ НЕУЯЗВИМА»),
которые никогда не попадали в словарь переводов вообще — то есть при
переключении интерфейса на английский язык эти конкретные фразы годами
оставались бы русскими прямо посреди английского текста. Важная деталь: ни
проверка типов (`tsc`), ни автоматические тесты (`vitest`) в принципе не
способны поймать такой пропуск — это обнаруживается только целенаправленной
сверкой строк вручную (или скриптом, который её автоматизирует).

### Отладочные инструменты фаз 6–13

- `/debug/spawn` — создать вторую сущность игроку с позывным `dev:DEBUG`,
  чтобы можно было вручную проверять поведение флотилии из нескольких
  сущностей (появился в фазе 6), работает рядом с уже существовавшим с
  фазы 5 маршрутом `/debug/credit`.
- `/debug/chain-key` — выдать себе ключ Цепи Миров без реального прохождения
  игрового цикла (фаза 11), защищён тем же самым паттерном
  `pid !== DEBUG_PID → 403`, что и остальные дебаг-маршруты.
- `server/scripts/wipe.ts --yes` — сброс игрового мира без затрагивания
  леджера начислений и конфига баланса (фаза 13, подробно описано выше).

### Как всё проверялось в фазах 6–13

`npm test` на сервере прогоняет все 65 тестов против настоящего PostgreSQL,
поднятого в Docker. На каждой отдельной фазе, ещё до перехода к живой
проверке в браузере, обязательно прогонялась проверка типов
(`npx tsc --noEmit`) во всех трёх пакетах — сервере, клиенте и общем
shared-пакете. Сборка клиента (`npx vite build`) на каждой фазе оставалась
чистой — те немногие предупреждения о доступности (accessibility) на
элементах `<pre role="button">` внутри карт сектора и галактики были там
изначально и не прирастали числом от фазы к фазе. Отдельно в фазе 12, после
добавления Rust-плагина `tauri-plugin-http`, проверялась компиляция и
регистрация плагина через `cargo check`, а схема прав доступа `http:default`
буквально сверялась с автоматически сгенерированным файлом
`client/src-tauri/gen/schemas/desktop-schema.json` — то есть не
предполагалась, а проверялась по факту. Полный запуск `npm run tauri dev`
в той же фазе подтвердил чистый старт всего стека без единой ошибки, но
не был докликан вживую внутри самого нативного окна — инструменты
браузерной автоматизации, которыми проверялись все остальные фазы, попросту
не видят содержимое настоящего Tauri-окна операционной системы (подробнее
об этом ограничении — в `Strategy - Plan.md`, в блоке «Итог» фазы 12). И,
наконец, на каждой фазе с 6 по 13 проводилась живая сквозная проверка в
настоящем браузере против реально работающего dev-сервера — включая фазу
12, где для этого был по-настоящему установлен и запущен локальный Ollama
с моделью `qwen2.5:3b`, а не просто имитация ответа модели заглушкой.
